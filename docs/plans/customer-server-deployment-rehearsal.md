# แผนซ้อม Deploy และตรวจความพร้อม HAMS ก่อนใช้งานจริง

สถานะ: แผนทดสอบหลัง refactor ยังไม่ได้รันทดสอบหรือรับรอง deployment
อ้างอิง: [แผน refactor](customer-server-refactor.md), [ลำดับ ticket ล่าสุด](../../backend/.scratch/customer-server-refactor/map.md) และข้อตกลง D1–D9

ข้อมูลล่าสุด: ลูกค้ายืนยันใช้ Ubuntu Server แต่ยังต้องระบุรุ่นและสถาปัตยกรรม ทำ T1 บนระบบทีมก่อน; T2 ใช้ Ubuntu Server VM/เครื่องทีมที่ตรงเป้าหมายได้; T3 รอการเข้าถึง server ลูกค้าผ่าน SSH หรือช่องทางที่อนุญาต

## เป้าหมาย

ยืนยันเป็นลำดับว่าชุดโปรแกรมที่แก้แล้วติดตั้งใหม่ได้ ทำงานในรูปแบบ production ได้ และใช้งานบนเครือข่ายของลูกค้าได้จริง การทดสอบต้องครอบคลุมชุดที่นำไปติดตั้งและค่าตั้งของเครื่อง ไม่อาศัยเพียงการเปิดเว็บได้จากเครื่องพัฒนา

เริ่มทดสอบ T1 บนระบบทีมก่อนทราบรุ่นเครื่องลูกค้า โดยบันทึก OS/runtime และขอบเขตที่ทดสอบ เมื่อทราบ Ubuntu Server รุ่นและสถาปัตยกรรมแล้วจึงซ้อม T2 ด้วยชุดส่งมอบบนเป้าหมายที่ตรงกัน และตรวจ T3 บน server ลูกค้าก่อนเปิดจริง ผลผ่านบนระบบทีมใช้แทนการตรวจชุดแพ็กบน Ubuntu Server ไม่ได้

## ระดับการทดสอบ

| ระดับ | สภาพแวดล้อม | สิ่งที่ยืนยันได้ | สิ่งที่ยังต้องตรวจต่อ |
| --- | --- | --- | --- |
| T1 — โค้ดและการเชื่อมต่อ | เครื่องทีมพัฒนาและฐานข้อมูลทดสอบแยก | กฎงาน สิทธิ์ session/2FA วงจรรูป สถานะพยากรณ์ และการ build | การติดตั้งใหม่ systemd/service บน Ubuntu Server สิทธิ์โฟลเดอร์ proxy และเครือข่ายจริง |
| T2 — ซ้อมติดตั้งใหม่ | Ubuntu Server VM หรือเครื่องสะอาดที่ตรงรุ่น/สถาปัตยกรรมเป้าหมาย ใช้ชุด release และค่าตั้งแบบ production | ติดตั้งครบจากคู่มือ runtime/dependencies ทำงาน การเริ่มอัตโนมัติ รูปภายใน HTTPS และการใช้งานผ่าน LAN | ความต่างของรุ่น/runtime สิทธิ์และเครือข่ายลูกค้า หากยังไม่ใช่เครื่องจริง |
| T3 — ก่อนเปิดใช้งานที่ลูกค้า | server ลูกค้าและเครื่องผู้ใช้อีกเครื่องในเครือข่าย ใช้ข้อมูล/พื้นที่ทดสอบที่แยกชัดเจน | ชุด runtime และค่าตั้งจริง firewall/DNS/HTTPS/SMTP/สิทธิ์โฟลเดอร์ พร้อมเส้นทางงานหลัก | การติดตามหลังเริ่มใช้งานและแผนดูแลตามที่ตกลง |

การใช้ VM หมายถึงมี OS อีกชุดหนึ่งที่ตรงเป้าหมายและแยกจากเครื่องพัฒนา ใช้แทนเครื่อง server ในการซ้อม สามารถล้างและติดตั้งชุดทดสอบใหม่ได้โดยไม่แตะฐานข้อมูลใช้งานจริง ไม่จำเป็นต้องซื้อ server เพิ่มเพื่อเริ่ม T2 แต่ต้องตรวจว่ามีเครื่องและสิทธิ์ใช้งาน VM ที่เหมาะสม

## เตรียมชุดทดสอบ

1. ระบุ revision/รุ่นที่ต้องการส่งมอบ และสร้าง frontend/backend สำหรับ production จาก dependency ที่ล็อกไว้
2. ใช้ package/runtime dependencies ที่ตรงกับ Ubuntu Server รุ่น/สถาปัตยกรรมที่จะทดสอบ รวม Prisma client และไฟล์ decoder/native modules ที่จำเป็น การผ่าน build บนเครื่องพัฒนาที่มี devDependencies ครบยังไม่ยืนยันว่าชุด runtime ที่ส่งมอบครบ
3. รันชุด production จริง: frontend ที่ build แล้ว และ backend ที่ build แล้ว ใช้ `NODE_ENV=production` พร้อม proxy/HTTPS ตามสัญญา `/api` ไม่ใช้ Vite dev server หรือโหมด watch เป็นหลักฐานของ deployment
4. สร้างฐานข้อมูล ชื่อระบบ/URL โฟลเดอร์รูป และ secret/key สำหรับทดสอบแยกจาก production การแยกแค่ port ไม่ใช่หลักฐานแยก session/cookie หรือข้อมูลครบถ้วน
5. ใช้ข้อมูลและไฟล์สังเคราะห์ รวมบัญชีทดสอบและรูปที่ไม่ใช่ข้อมูลส่วนบุคคลจริง และจำกัดการส่งอีเมลไปยังปลายทางทดสอบที่กำหนด
6. สำหรับการซ้อม bootstrap แบบ production ต้องมี SMTP ทดสอบที่ผ่านนโยบาย TLS เดียวกับแอป ส่วน Mailpit ค่าเริ่มต้นสำหรับ development ไม่ใช่หลักฐานว่าส่งอีเมล production ได้

### แยกความครบถ้วนของชุด runtime กับเครื่องมือเตรียมระบบ

ปัจจุบัน `prisma`, `tsx` และ `sharp` อยู่ใน devDependencies ของ backend แต่การ migrate/seed/bootstrap/handover ต้องใช้เครื่องมือหรือ scripts ที่เกี่ยวข้อง และการแปลงรูปภายในจะต้องมี processor ใน runtime จึงต้องออกแบบการแพ็กให้ครบตามหน้าที่: ชุด runtime มี dependencies/Prisma client/decoder ที่แอปต้องใช้จริง ส่วนชุดเตรียมระบบมีเครื่องมือหรือ scripts ที่แพ็ก/compile ไว้โดยตั้งใจ ไม่สมมติว่าการติดตั้งเฉพาะ production dependencies จะทำทุกขั้นตอนส่งมอบได้แล้ว

ต้องระบุขั้นตอน generate Prisma client และการนำไฟล์ WASM/decoder ไปไว้ในชุดส่งมอบอย่างชัดเจน Nest build ที่มีอยู่ยังไม่ใช่หลักฐานว่าบันเดิลไฟล์เหล่านี้ครบ การซ้อม R01 และ R10 ต้องเริ่มด้วยชุดที่แพ็กจริงและไม่มี dependencies จาก checkout พัฒนาช่วยอยู่

## T1 — ตรวจโค้ดและฐานข้อมูลก่อนซ้อมติดตั้ง

- ตรวจ frontend build, type checks และชุดทดสอบที่เกี่ยวข้องกับส่วนที่แก้
- ตรวจ backend build และชุดทดสอบที่ครอบคลุม HTTP authentication/session, 2FA, การอนุญาตอัปโหลด/อ่านรูป, วงจรแนบ/เปลี่ยน/ลบรูป และฟีเจอร์พยากรณ์
- บังคับฐานข้อมูลทดสอบที่แยกจริงก่อน import/เริ่มชุดทดสอบทุกทาง ต้องตรวจ `DATABASE_URL` ที่ถูกใช้จริง ไม่อาศัยชื่อคำสั่งว่าคือ unit test
- ตรวจ harness เดิมและเพิ่ม guard ที่จำเป็นก่อนรันทดสอบรวม: ชุด auth-integration มีการบังคับ `TEST_DATABASE_URL` แต่ไม่ได้หมายความว่าทุก suite ในคำสั่งทั่วไปมี guard เดียวกัน
- แยกผลของ tests ที่ใช้ provider/clock จำลองออกจากผลการเรียก local storage จริงและ Cloudinary จริง เมื่อ D1 ต้องคง cloud ต้องมีหลักฐานการทำงานของ provider ที่เกี่ยวข้องด้วยบัญชี/ไฟล์ทดสอบ
- ผลผ่านของชุดที่ใช้ auth หรือ storage จำลองใช้ยืนยันเฉพาะขอบเขตนั้น ยังไม่แทนการทดลอง browser ผ่าน HTTPS กับไฟล์และ service ที่ติดตั้งจริง

หลักฐานที่ต้องใช้กำหนดทางรันทดสอบ: [auth-integration setup](../../backend/test/auth-integration-setup.ts) มี guard/redirect ฐานทดสอบ แต่ [trusted-browser service tests](../../backend/src/auth/trusted-browser.service.spec.ts) และ [two-factor service tests](../../backend/src/auth/two-factor.service.spec.ts) ใช้ shared Prisma และลบ fixture rows โดยไม่มี guard เดียวกันในไฟล์นั้น นอกจากนี้ [generic e2e config](../../backend/test/jest-e2e.json) จำลอง auth ขณะที่ [image auth-integration](../../backend/test/image-uploads.auth-integration.e2e-spec.ts) ใช้ storage/clock จำลอง จึงต้องแยกผลที่พิสูจน์ได้ของแต่ละ suite ก่อนสรุปความพร้อม

## T2 — ซ้อมติดตั้งบน Ubuntu Server ที่สะอาด

| หมายเลข | สถานการณ์ | เกณฑ์ผ่าน |
| --- | --- | --- |
| R01 | ติดตั้งจากคู่มือบนเครื่องที่ไม่มีสภาพแวดล้อมพัฒนาของทีม | เตรียม runtime/configuration, migrate deploy, reference seed และเริ่มแอปได้โดยไม่ต้องอาศัยไฟล์ลับ/แพ็กเกจที่ตกค้างจากเครื่องพัฒนา |
| R02 | เปิดจาก browser อีกเครื่องผ่านชื่อระบบและ HTTPS | หน้าเว็บ/API ใช้งานได้ session cookie/CSRF ทำงาน เปิดหน้าโดยตรงและ refresh ไม่หลุดไปเส้นทางผิด และ notification SSE ทำงานผ่าน proxy |
| R03 | เปิดบัญชีทดสอบตามขั้นตอนจริง | bootstrap ผู้ดูแล ส่งอีเมลยืนยัน เข้าสู่ระบบ enroll 2FA และตรวจ handover ด้วยบัญชีทดสอบได้ |
| R04 | ทำงานหลักด้วยบทบาทที่เกี่ยวข้อง | ลงทะเบียนครุภัณฑ์ ยืมคืน แจ้งซ่อมและดำเนินขั้นตอนที่จำเป็น บันทึกข้อมูลแล้วเปิดอ่านใหม่ได้ พร้อมตรวจสิทธิ์ที่ถูกปฏิเสธด้วย |
| R05 | ส่งรูป JPEG/PNG/WebP/HEIC/HEIF ตัวอย่าง | รูปที่ผ่านเกณฑ์ถูกแปลงตามนโยบายจริง orientation/ขนาดถูกต้อง; ไฟล์เสียหรือเกินขนาดถูกปฏิเสธโดยไม่ทำให้รูปเดิมหาย |
| R06 | เปิดรูปตามสิทธิ์และอายุลิงก์ | รูปครุภัณฑ์เปิดจากลิงก์ได้ในเครือข่าย; รูปบุคลากรไม่เป็นไฟล์ public ถาวร และคำขออ่านใหม่จากลิงก์หมดอายุถูกปฏิเสธ |
| R07 | เปลี่ยนรูป บันทึกซ้ำ และจำลองคำขอขาดช่วง | รูปที่ผูกกับข้อมูลจริงไม่หายเมื่อบันทึกล้มเหลว/ไม่ทราบผล และ cleanup ไม่ลบรูปที่ยังใช้อยู่ |
| R08 | ปิด Gemini และปิดการออกอินเทอร์เน็ตสาธารณะ | หลังเปิดบัญชีแล้ว login/2FA งานหลัก รูป และหน้าเว็บผ่าน LAN ได้; ไม่ขอรูป/font จาก Cloudinary/Google; LAN และเส้นทางบริการภายในยังทำงาน |
| R09 | Gemini ปิด/เปิด/ติดต่อไม่ได้ | เมื่อปิดไม่มีคำขอออก; เปิดเฉพาะเมื่อมีสิทธิ์และค่าตั้งสำหรับการทดสอบ; เมื่อใช้ไม่ได้ยังดูข้อมูลย้อนหลังได้ และไม่แสดงว่าอนาคตเป็นศูนย์บาท |
| R10 | เริ่มผ่านบัญชี service และ working directory ที่จะใช้ | อ่าน configuration/decoder และเขียนโฟลเดอร์ข้อมูลได้ตามสิทธิ์ ไม่พึ่งการเปิดโปรแกรมจากโฟลเดอร์ source ด้วยบัญชีผู้พัฒนา |
| R11 | รีสตาร์ต service และ reboot เครื่องทดสอบ | แอปเริ่มตามขั้นตอนอัตโนมัติ ข้อมูล รูป และ key ยังคงเดิม ทดสอบล็อกอินและดูรูปหลังเริ่มใหม่ได้ |
| R12 | อัปเดตระหว่างช่วงพักใช้งานที่จำลองไว้ | ใช้ชุด release ใหม่กับข้อมูลทดสอบเดิมและโฟลเดอร์รูปเดิมได้ ไม่มี reset/demo seed หรือไฟล์รูปถูกทับ |
| R13 | ทดลองวิธีย้อนกลับและกู้คืนตามคู่มือ | IT ใช้เครื่องมือที่เลือกคืนข้อมูลลงปลายทางทดสอบแยก แล้วตรวจฐานข้อมูล รูป และ key ที่ต้องใช้ร่วมกันได้ ไม่สร้างเครื่องมือ backup ใหม่ตาม D8B |
| R14 | ใช้งานพร้อมกันและอัปโหลดรูปตามภาระงานเป้าหมาย | จำนวนผู้ใช้/รูปและเกณฑ์เวลาตอบสนองตกลงก่อนรัน; วัด CPU/RAM/พื้นที่และการใช้ memory ของ decoder ไม่ให้การแปลงรูปขวางงานหลัก |

R08 ไม่ได้อ้างว่า SMTP ภายนอกหรือ Gemini ทำงานได้เมื่อออกอินเทอร์เน็ตไม่ได้ การส่งอีเมลต้องตรวจแยกบนเส้นทางที่ตั้งไว้ และ Gemini เป็นตัวเลือกที่ปิดได้ตามข้อตกลง

การอ่านรูปที่หมดอายุใน R06 หมายถึงคำขอไฟล์ใหม่ ไม่ใช่การอ้างว่าจะลบรูปที่ browser ดาวน์โหลดไปแล้ว

## T3 — ตรวจบนเครื่องลูกค้าก่อนเปิดใช้งานจริง

- ยืนยัน Ubuntu Server รุ่น/สถาปัตยกรรม, Node/PostgreSQL, OpenSSH และชุดแปลงรูปที่ใช้งานจริง บันทึกความต่างจาก T2 และตรวจซ้ำส่วนที่ได้รับผล
- ใช้ชุด release ที่ผ่าน T2 และค่าตั้งที่ตรวจแล้ว หากแพ็กใหม่หรือเปลี่ยน dependency/runtime ให้ทดสอบชุดที่เปลี่ยนก่อนใช้
- ทดสอบจากเครื่องเจ้าหน้าที่อีกเครื่อง ตรวจ DNS/HTTPS/firewall/proxy และสิทธิ์โฟลเดอร์ของบัญชี service ไม่พอเพียงการเปิด `localhost` บน server
- ตรวจ SMTP ที่ลูกค้าอนุญาตด้วยปลายทางทดสอบที่กำหนด ทั้งการส่งจริงและการเปิดลิงก์จากเครื่องผู้ใช้
- ทบทวน R02–R06, R08 และ R10–R11 บนสภาพแวดล้อมจริงที่แยกข้อมูลทดสอบอย่างเหมาะสม การ reboot/หยุด service บนเครื่องลูกค้าต้องอยู่ในช่วงที่นัดหมายและไม่กระทบระบบอื่นที่ไม่ได้อยู่ในงาน
- เตรียม production ใหม่ด้วยข้อมูลอ้างอิงและข้อมูลจริงตาม D2 ตรวจผู้ดูแลจริงสองบัญชี อีเมลและ 2FA ตาม handover gate เดิม
- ยืนยันคู่มือ backup/restore และผู้รับผิดชอบ IT ตาม D8B รวมช่วงอัปเดตนอกเวลาราชการตาม D9A

## หลักฐานและเกณฑ์เปิดใช้งาน

เก็บรายงานต่อชุด release: revision/build identifier, รุ่น OS/runtime, ค่าตั้งที่มีผลโดยไม่บันทึก secret, กรณีทดสอบที่รันจริง, ผลผ่าน/ไม่ผ่าน, log หรือภาพหน้าจอที่จำเป็น และผู้ตรวจผล แยกสิ่งที่ทดสอบแล้วออกจากสิ่งที่ยังไม่ได้ทดสอบอย่างชัดเจน

เกณฑ์พร้อมเปิดใช้งานคือกรณีที่จำเป็นต่อรูปแบบติดตั้งนั้นผ่าน ไม่มีปัญหาค้างที่ทำให้งานหลักหรือสิทธิ์ข้อมูลผิด และผ่าน T3 กับเครื่องลูกค้า การที่ Gemini ปิดตามข้อตกลงถือเป็นสภาพใช้งานที่ถูกต้อง ส่วนการไม่มี SMTP ที่ส่งได้จริงยังไม่ผ่านเงื่อนไขเปิดใช้งาน

แผนนี้เป็นวิธีสร้างหลักฐานความพร้อม ไม่ใช่ผลการทดสอบที่เกิดขึ้นแล้ว และไม่รับรองเครื่องที่ยังไม่ได้ตรวจ
