สเปกสำหรับดำเนินงาน: [Customer Server Refactor and Deployment Verification](../../backend/.scratch/customer-server-refactor/spec.md) เผยแพร่ใน Local Markdown issue tracker ของโครงการด้วยสถานะ `ready-for-agent`

ข้อมูลล่าสุดจากผู้ใช้: ลูกค้ายืนยันใช้ Ubuntu Server และกำลังเตรียมการเข้าถึงผ่าน SSH ให้ยึด [ลำดับ ticket ล่าสุด](../../backend/.scratch/customer-server-refactor/map.md): ทำ 01–06 บนระบบทดสอบทีมก่อน เก็บรุ่น/สถาปัตยกรรมเพื่อแพ็กและซ้อมบน Ubuntu Server ใน 07–08 และรอการเข้าถึงเครื่องจริงสำหรับ 09 ข้อมูลนี้ใช้แทนสมมติฐาน Windows เดิม โดยยังคง D1–D9

## ภาพรวมของแผน

ใช้ HAMS โค้ดชุดเดียวสำหรับการติดตั้งบน cloud และ server ลูกค้า โดยการติดตั้งที่ลูกค้าเริ่มฐาน production ใหม่ เก็บรูปในโฟลเดอร์ข้อมูลภายใน และให้งานหลักใช้ผ่าน LAN ได้โดยไม่พึ่งอินเทอร์เน็ตสาธารณะหลังติดตั้งและเปิดบัญชี

| ส่วน | รูปแบบ cloud | รูปแบบ server ลูกค้า |
| --- | --- | --- |
| เว็บและ API | คงเส้นทางใช้งานเดิมและการเลือกค่าตั้งของระบบ cloud | เสิร์ฟเว็บ/API ภายในผ่าน HTTPS และเส้นทาง `/api` ของเว็บ |
| ฐานข้อมูล | PostgreSQL ตามปลายทางที่กำหนดสำหรับ cloud | PostgreSQL ใหม่ในเครื่องหรือเครือข่ายของลูกค้า |
| รูป | Cloudinary ตามพฤติกรรมเดิม | โฟลเดอร์ข้อมูลที่ตั้งตำแหน่งได้ แยกจากโค้ด |
| อีเมล | SMTP ตามค่าตั้งของการติดตั้งนั้น | SMTP ที่ลูกค้าอนุญาต เป็นเงื่อนไขก่อนเปิดใช้งานจริง |
| พยากรณ์ | เปิดใช้ได้ตามค่าตั้งที่ชัดเจน | ปิดเป็นค่าเริ่มต้น เปิดได้เมื่อมีสิทธิ์และค่าตั้งครบ |
| ไฟล์หน้าเว็บและ font | ใช้ไฟล์ที่เตรียมไว้กับแอปได้ | ต้องไม่พึ่งบริการภายนอกสำหรับงานหลัก |

งานหลักคือจัดขอบเขตค่าตั้งและที่เก็บรูป เพิ่มการรับ/แปลง/อ่านไฟล์ภายใน ปรับ frontend ให้ใช้ได้ทั้งสองที่เก็บ แยกสถานะพยากรณ์ และเตรียมคู่มือติดตั้ง/ดูแล การย้ายข้อมูล demo เดิม การทำโมเดลพยากรณ์ภายใน การเปิดบัญชีโดยไม่ใช้อีเมล และการสร้างเครื่องมือ backup/restore ใหม่อยู่นอกขอบเขตที่เลือก

ข้อมูลที่ยังต้องขอจากลูกค้าเป็นข้อมูลก่อนติดตั้งจริง ได้แก่ OS/runtime ที่ลูกค้ายืนยันและรองรับ สิทธิ์ติดตั้งและโฟลเดอร์ โดเมน/HTTPS ปลายทาง SMTP นโยบาย Gemini และรายละเอียดการดูแลสำรองข้อมูล ข้อมูลเหล่านี้ไม่ใช่คำถามด้านขอบเขตที่ยังค้างในการสัมภาษณ์ครั้งนี้

## เป้าหมายและข้อมูลที่ผู้ใช้ยืนยันแล้ว

- เตรียมปรับโครงสร้างโค้ด HAMS เพื่อย้ายจากบริการภายนอกไปติดตั้งบนเครื่องของลูกค้า
- OS เป้าหมายคือ Ubuntu Server ลูกค้ากำลังเตรียมการเข้าถึงผ่าน SSH และยังต้องยืนยันรุ่น สถาปัตยกรรม สิทธิ์ sudo และข้อจำกัดการติดตั้งก่อนแพ็กชุดส่งมอบ
- ทีมติดตั้งสามารถเข้าไปตั้งค่า server ระหว่าง deploy ได้ ขอบเขตสิทธิ์ติดตั้งโปรแกรมและปรับเครือข่ายยังไม่ได้ตรวจจากเครื่องจริง
- ยังไม่ทราบว่าลูกค้ามี SMTP หรืออนุญาตให้เรียก Gemini หรือไม่
- วางแผนและปรับส่วนแอปที่ไม่ขึ้นกับเครื่องได้ก่อน ส่วนวิธีติดตั้งเฉพาะเครื่องต้องรอข้อมูลสภาพแวดล้อม
- สาขาที่ตรวจขณะเริ่มวางแผน: `refactor/customer-server-refactor`

การเข้าถึง server เพื่อตั้งค่าระหว่าง deploy ไม่ถือเป็นข้อยืนยันว่าลูกค้าอนุญาตให้ส่งข้อมูลไปบริการภายนอก

## ข้อตกลงที่ยืนยันจากการสัมภาษณ์

ผู้ใช้ตอบ `1A, 2A, 3A, 4A` เมื่อ 2026-10-17:

1. **D1 — โค้ดชุดเดียว รองรับสองรูปแบบติดตั้ง:** คง cloud เดิมและเพิ่มการติดตั้งบน server ลูกค้า เลือกบริการที่เกี่ยวข้องผ่านค่าตั้ง ดู [ADR 0001](../adr/0001-support-cloud-and-customer-server.md)
2. **D2 — เริ่ม production ใหม่:** ใช้ production reference seed และข้อมูลจริงของลูกค้า งานรอบนี้ไม่รวมการย้ายข้อมูล บัญชี รูป หรือ session จากระบบ demo/cloud เดิม
3. **D3 — Gemini เป็นฟีเจอร์ที่ปิดได้:** ปิดการพยากรณ์ได้โดยยังแสดงรายจ่ายย้อนหลังและการวิเคราะห์อายุครุภัณฑ์ ไม่มีงานพัฒนาระบบพยากรณ์ภายในทดแทนในรอบนี้
4. **D4 — SMTP ยังเป็นเงื่อนไขก่อนเปิดใช้งานจริง:** คงการยืนยันอีเมล การส่งข้อมูลผู้ดูแลเริ่มต้น และการแจ้งเรื่องการกู้คืนบัญชี ต้องเตรียม SMTP ที่ลูกค้าอนุญาตและตรวจการส่งถึงผู้ใช้ก่อนเปิดระบบ ไม่มีงานออกแบบการเปิดบัญชีโดยไม่ใช้อีเมลในรอบนี้

ผู้ใช้ตอบ `5A, 6A, 7A` ในรอบถัดมา:

5. **D5 — เก็บรูปของลูกค้าใน filesystem:** ใช้โฟลเดอร์ข้อมูลบน server ลูกค้าที่ตั้งตำแหน่งได้และแยกจากโฟลเดอร์โค้ด การอัปเดตแอปต้องไม่ลบหรือทับไฟล์ที่ผูกกับข้อมูลจริง ดู [ADR 0002](../adr/0002-customer-local-images-and-lan-operation.md)
6. **D6 — คงกฎการอ่านรูปเดิม:** รูปครุภัณฑ์เปิดผ่านลิงก์ได้เมื่อเข้าถึงเครือข่ายของ server ส่วนรูปประจำบุคลากรต้องผ่านการอนุญาตจาก HAMS; ไม่ได้กำหนดให้เปิด server ลูกค้าสู่อินเทอร์เน็ต
7. **D7 — งานหลักใช้ได้ภายใน LAN:** หลังติดตั้งและเปิดบัญชีแล้ว งานทะเบียน ยืมคืน ซ่อม และรูปของการติดตั้งที่ลูกค้าต้องใช้งานผ่าน LAN ได้เมื่อไม่มีอินเทอร์เน็ตสาธารณะ SMTP ยังต้องเข้าถึงปลายทางที่ตั้งไว้ และ Gemini ต้องมีอินเทอร์เน็ตเมื่อได้รับอนุญาตและเปิดใช้

ผู้ใช้ตอบ `8B` และต่อมายืนยัน `9A`:

8. **D8 — ส่งมอบคู่มือสำรอง/กู้คืน:** ทีมพัฒนาจัดทำคู่มือรายการที่ต้องสำรอง ขั้นตอนและเกณฑ์ตรวจคืนฐานข้อมูลพร้อมรูป ส่วน IT ลูกค้าจัดหาเครื่องมือเอง งานรอบนี้ไม่รวมการพัฒนาสคริปต์ backup/restore หรือระบบตั้งตารางสำรองใหม่

9. **D9 — ยอมรับช่วงดูแลระบบตามนัด:** ผู้ใช้ยืนยันว่าระบบใช้ในเวลาราชการตามปกติและไม่ได้ทำงานตลอด 24 ชั่วโมง จึงนัดพักใช้งานเพื่ออัปเดตหรือดูแลข้อมูลนอกเวลางานได้ ต้องกำหนดช่วงเวลาจริงและแจ้งลูกค้าก่อนดำเนินการ ไม่ได้กำหนดระยะหยุดสูงสุดหรือรับรองว่าสามารถหยุดเครื่องได้โดยไม่ต้องนัดหมาย ดู [ADR 0003](../adr/0003-office-hours-planned-maintenance.md)

ข้อตกลง D1 ไม่ได้รวมการสลับ provider ของฐานข้อมูล production ที่มีรูปอยู่แล้วแบบอัตโนมัติ และ D2 ไม่รวมเครื่องมือนำเข้าข้อมูลจริงรูปแบบใหม่หากยังไม่ได้ตกลงเพิ่มเติม

## ข้อเท็จจริงจากโค้ดและเอกสารเดิม

| ส่วน | พฤติกรรมที่ตรวจพบ | ผลต่อแผน |
| --- | --- | --- |
| ฐานข้อมูล | ใช้ PostgreSQL ผ่าน Prisma/pg และอ่านปลายทางจาก `DATABASE_URL` | เริ่มฐาน production แยกตาม D2 และใช้ migrations สำหรับ production แทนการ reset หรือ demo seed |
| หน้าเว็บ | Browser เรียก API ด้วยเส้นทาง `/api` บน origin เดียวกับหน้าเว็บ | วิธีเสิร์ฟเว็บและส่งต่อ API บนเครื่องลูกค้าต้องรองรับสัญญานี้และ HTTPS |
| รูปภาพ | Backend เลือก `CloudinaryStorageAdapter` โดยตรง และ frontend ยอมรับ URL รูปเฉพาะ Cloudinary | เพิ่มที่เก็บรูปภายในต้องพิจารณาทั้ง backend และ frontend รวมถึงการตรวจ URL และสิทธิ์อ่านรูป |
| การรับและประมวลผลรูป | Browser อัปโหลดตรงไป Cloudinary และตรวจผลตามรูปแบบ Cloudinary; Cloudinary ยังหมุน/ย่อ/แปลง JPEG และลบ metadata ให้ | ต้องออกแบบเส้นทางรับไฟล์และความสามารถประมวลผลทดแทน การเปลี่ยนชื่อโฟลเดอร์หรือ adapter อย่างเดียวไม่พอ |
| การอ้างอิงและลบรูป | ข้อมูลรูปและงานลบค้างระบุ provider/account; มีข้อกำหนดฐานข้อมูลเกี่ยวกับ version และชนิดการอ่านรูป | หากมีข้อมูลเก่าต้องวางแผนรูปและ cleanup jobs ควบคู่กับฐานข้อมูล |
| บัญชีผู้ใช้ | Authentication บังคับยืนยันอีเมล | การไม่ตั้ง SMTP ไม่เท่ากับรองรับการเปิดใช้งานบัญชีโดยไม่ใช้อีเมล |
| ผู้ดูแลเริ่มต้น | Bootstrap ต้องมี SMTP และ TLS เพื่อส่งข้อมูลเริ่มต้นและอีเมลยืนยัน ส่วนการส่งมอบตรวจผู้ดูแลจริงสองบัญชี | คงเงื่อนไข SMTP ตาม D4 พร้อมตรวจการส่งถึงผู้ใช้ก่อนเปิดระบบ |
| พยากรณ์ | เรียก Gemini เมื่อข้อมูลเพียงพอ ไม่มีสวิตช์ปิดอย่างชัดเจน; กรณีไม่มี key หรือเรียกไม่สำเร็จคืนประวัติพร้อมผลพยากรณ์ว่าง | ต้องกำหนดสถานะฟีเจอร์ที่ปิดและพฤติกรรมหน้าจอให้ชัด การเว้น key ไม่ใช่โหมดใช้งานที่ออกแบบไว้ครบถ้วน |
| หน้าพยากรณ์ | ยังไม่แสดง `message`/`has_sufficient_data` จาก API และใช้ศูนย์กับ KPI เมื่อผลพยากรณ์ว่าง | โหมดปิดหรือขัดข้องต้องสื่อว่าไม่มีผลพยากรณ์ เพื่อให้ผู้ใช้ไม่เข้าใจว่าเป็นคำทำนายรายจ่ายศูนย์บาท |
| ข้อมูลเริ่มต้น | มี production reference seed แยกจากข้อมูล demo และมีขั้นตอน bootstrap ผู้ดูแล | เริ่ม production ใหม่ตาม D2 และเตรียมข้อมูลจริงของลูกค้าแยกจาก demo |
| Runtime และชุดติดตั้ง | README ยังแนะนำ Node 18+ แต่ Nest/Prisma/Vite ที่ติดตั้งในเครื่องพัฒนาต้องการรุ่นใหม่กว่า; Compose มีเฉพาะ PostgreSQL กับ Mailpit | ต้องระบุ runtime ที่สอดคล้องกับ dependency ที่ล็อกและตรวจบน Ubuntu Server รุ่น/สถาปัตยกรรมจริง; ชุด Compose เดิมยังไม่ใช่ชุดติดตั้งแอป production |
| การติดต่อภายนอกอื่น | CSS ดึง font จาก Google Fonts | D7 กำหนดให้เสิร์ฟ font ภายในหรือใช้ font ของเครื่อง พร้อมตรวจคำขอภายนอกในโหมดลูกค้า |

การเรียก Gemini ปัจจุบันส่งวันที่และยอดค่าใช้จ่ายรายเดือนจริง พร้อมตัวเลขสรุปอายุการใช้งานครุภัณฑ์ ตัวแปร `is_data_masked` ใน response ไม่ใช่หลักฐานว่ามีการปิดบังยอดค่าใช้จ่ายก่อนส่งออก ไม่มีระบบพยากรณ์ภายในที่ทำหน้าที่แทน Gemini อยู่แล้ว ส่วนคำว่า fallback model ในโค้ดหมายถึงการลอง Gemini รุ่นอื่น

## ภาษาของระบบและข้อกำหนดเดิมที่เกี่ยวข้อง

ใช้คำนิยามใน [Business Domain](../../backend/CONTEXT.md#business-domain) และ [คำศัพท์สำหรับแผนส่งมอบ](../CONTEXT.md) เป็นฐาน:

- **Employee Photo / รูปประจำบุคลากร** เป็นรูปที่มีเงื่อนไขยืนยันตัวตนและการเข้าใช้งาน HAMS
- **Asset Image / รูปครุภัณฑ์** เป็นรูปประกอบทะเบียนซึ่งข้อกำหนดเดิมอนุญาตให้ผู้มีลิงก์อ่านได้

ความต่างของรูปสองประเภทนี้ต้องมีผลต่อการออกแบบที่เก็บรูปใหม่ การย้ายที่เก็บรูปเพียงอย่างเดียวยังไม่ใช่ข้อสรุปว่าจะเปลี่ยนสิทธิ์อ่านรูป

ในข้อกำหนดเดิม **การเปิดรูปครุภัณฑ์จากลิงก์โดยไม่ต้องล็อกอิน** หมายถึงไม่ตรวจ session ของ HAMS สำหรับไฟล์นั้น ไม่ได้กำหนดว่าต้องเปิด server ลูกค้าให้เข้าถึงจากอินเทอร์เน็ต ส่วนรูปประจำบุคลากรต้องผ่านการอนุญาตออกลิงก์ก่อน โดยผู้มีลิงก์ชั่วคราวอาจอ่านไฟล์ได้จนกว่าลิงก์หมดอายุ แม้ไม่ได้ส่ง session ของ HAMS ไปยังที่เก็บรูป

อ้างอิง [image specification](../../backend/docs/specs/image-upload-storage-abstraction.md), [ADR 0004](../../backend/docs/adr/0004-short-lived-image-read-links.md), [ADR 0005](../../backend/docs/adr/0005-employee-photo-cache-and-isolated-fe-handoff.md) และ [session specification](../../backend/docs/specs/two-factor-authentication-and-browser-sessions.md) ก่อนตัดสินใจเปลี่ยนพฤติกรรมเดิม

ยังไม่มีคำศัพท์ธุรกิจใหม่ที่ตกลงเพิ่มเติม การรองรับสองรูปแบบติดตั้งบันทึกเป็น [ADR 0001](../adr/0001-support-cloud-and-customer-server.md) ส่วนคำนิยามรูปสองประเภทจะใช้ตรวจการตัดสินใจเรื่องสิทธิ์อ่านในรอบถัดไป

## ข้อกำหนดรูปภาพที่สืบทอดและข้อเท็จจริงรอบที่ 2

คงข้อกำหนดไฟล์ JPEG, PNG, static WebP และ HEIC/HEIF ตาม [image specification](../../backend/docs/specs/image-upload-storage-abstraction.md#confirmed-heic-acceptance-and-upload-time-conversion) การ refactor ไม่ถือเป็นการอนุญาตให้ลดรูปแบบไฟล์ที่ผู้ใช้ใช้งานได้ การเลือกตัวแปลงและแพ็กเกจเป็นงานทางวิศวกรรมที่ต้องพิสูจน์ตาม runtime จริง

- ต้นฉบับไม่เกิน 10,000,000 bytes และ 25,000,000 pixels; ผลลัพธ์เป็น JPEG quality 80 พร้อมปรับ orientation, พื้นหลังขาวสำหรับความโปร่งใส, ไม่ขยายภาพเล็ก และรักษานโยบาย metadata เดิม
- ขนาดด้านยาวไม่เกิน 1,600 pixels สำหรับรูปครุภัณฑ์ และ 512 pixels สำหรับรูปประจำบุคลากร
- Sharp ที่ล็อกในโครงการคือ 0.33.5 และอยู่ใน devDependencies ยังไม่มี local normalization ใน runtime การพบแพ็กเกจนี้ไม่ได้พิสูจน์ว่า production ประมวลผลรูปได้แล้ว
- เอกสาร [Sharp 0.33.5](https://github.com/lovell/sharp/blob/v0.33.5/docs/install.md) และ [HEIF API](https://sharp.pixelplumbing.com/api-output/#heif) แสดงว่าการรองรับ HEIC/HEVC ขึ้นกับ codec/build ที่รวมอยู่ การมี Sharp ใน dependency จึงยังไม่ใช่หลักฐานว่าชุด production บน Ubuntu Server ประมวลผลไฟล์จากโทรศัพท์ได้ครบ
- เก็บการแปลงรูปไว้หลังขอบเขตที่เปลี่ยน implementation ได้ และตรวจ Ubuntu Server รุ่น/สถาปัตยกรรม/runtime/codec กับไฟล์ตัวอย่างจริงก่อนประกาศรองรับ HEIC บนเครื่องเป้าหมาย การตัด HEIC ออกต้องเป็นการตัดสินใจแก้ขอบเขตต่างหากหากพบว่าทำตามข้อกำหนดไม่ได้
- การย้าย provider ต้องรักษาวงจร intent → upload/normalize → verify → pending → attach → cleanup และการกู้สถานะเมื่อบันทึกสำเร็จแต่ response สูญหาย ไม่ลบรูปปัจจุบันเมื่อเปลี่ยนรูปไม่สำเร็จ
- การเลือกวิธีส่งไฟล์ รูปแบบหลักฐานอัปโหลด ชื่อ route การป้องกัน path traversal การเขียนไฟล์แบบ atomic และขอบเขต timeout/concurrency เป็นรายละเอียดทางวิศวกรรม ไม่ใช่ข้อเท็จจริงที่ให้ผู้ใช้เดา

### ทางเลือกที่ต้องพิสูจน์สำหรับ HEIC

มีทางเลือกถอดรหัส HEIC เป็น pixels ภายในเครื่องผ่าน [libheif-js แบบ bundled WASM](https://github.com/catdad-experiments/libheif-js#usage) แล้วส่ง pixels ให้ตัวแปลง JPEG เพื่อย่อรูปและทำ normalization ตามนโยบายเดิม หรือทดลอง wrapper [heic-decode](https://github.com/catdad-experiments/heic-decode#usage) เป็นจุดเริ่มต้น ทั้งสองทางใช้ decoder ตระกูลเดียวกันและยังไม่ใช่ dependency ที่เลือกแล้ว

การทดลองหลังยืนยันแผนต้องตรวจ orientation/mirroring และภาพหลักของไฟล์ HEIF, ความถูกต้องของสี, การใช้ memory, timeout/concurrency และการทำงานจากชุดติดตั้งที่ไม่ใช้อินเทอร์เน็ต/ไม่ขึ้นกับ working directory โดยใช้ไฟล์ตัวอย่างที่ไม่ใช่ข้อมูลส่วนบุคคลจริง API ของ wrapper ที่คืน Promise ยังอาจใช้ CPU แบบ synchronous จึงต้องแยกงานถอดรหัสที่มีขอบเขตชัดเจน ไม่ให้ขวางคำขอหลักของแอป

ตัวอย่าง memory ขั้นต่ำจากขนาดภาพ: RGBA ของภาพ 25,000,000 pixels มีขนาด 100,000,000 bytes ยังไม่รวม decoder, ต้นฉบับ, สำเนาข้อมูล และตัวแปลง JPEG ต้องอ่านขนาดภาพและจำกัดทรัพยากรก่อนจัดสรรข้อมูลของ HAMS และวัดการใช้ memory จริงก่อนกำหนดจำนวนงานพร้อมกัน การย่อภาพปลายทางไม่ได้กำจัดต้นทุนของการ decode ภาพเต็ม

ตาม D5 และ D6 การติดตั้งที่ลูกค้าใช้ filesystem ภายในและคงกฎการอ่านรูปสองประเภทตามเดิม พร้อมรักษา Cloudinary สำหรับรูปแบบ cloud

| D8 — สิ่งที่ส่งมอบด้าน backup/restore | ทีมพัฒนาเตรียมเครื่องมือและคู่มือสำรอง/กู้คืนฐานข้อมูลพร้อมรูป ให้ IT ลูกค้าตั้งตารางและดูแลหลังส่งมอบ | ทีมพัฒนาเตรียมเฉพาะคู่มือรายการข้อมูลและเกณฑ์ตรวจคืน โดย IT ลูกค้าจัดเครื่องมือเอง | ข้อเสนอเดิม A; ผู้ใช้เลือก B จึงยึดขอบเขตคู่มือและเกณฑ์ตรวจคืน | 8B — IT จัดเครื่องมือเอง |

ตาม D8B และ D9A ให้ส่งมอบคู่มือสำหรับ IT และรองรับขั้นตอนดูแล/อัปเดตแบบนัดพักใช้งานนอกเวลาราชการ ไม่ต้องเพิ่มสถาปัตยกรรมอัปเดตโดยรับรายการต่อเนื่องในงานรอบนี้ การมีช่วงพักใช้งานไม่ได้ตัดข้อกำหนดเก็บฐานข้อมูลและไฟล์ให้สอดคล้องกัน

สถานการณ์ที่ยอมรับตาม D9A: ทีมติดตั้งนัดช่วงนอกเวลาราชการเพื่อลง HAMS รุ่นใหม่ รอรายการที่กำลังบันทึกให้เสร็จ หยุดแอปตามขั้นตอน อัปเดตหรือดำเนินการดูแลตามคู่มือ แล้วตรวจการเริ่มทำงานและความครบถ้วนของข้อมูลก่อนเปิดใช้งานอีกครั้ง ช่วงเวลาจริงยังต้องวัดและนัดหมาย ไม่ได้สมมติจำนวนผู้ใช้งานหรือระยะหยุดสูงสุด

การสำรองข้อมูลไม่ได้จำเป็นต้องหยุดระบบทุกวิธี การเลือกเครื่องมือของ IT และวิธีเก็บฐานข้อมูลกับไฟล์ให้สอดคล้องกันจะระบุว่าต้องมีช่วงพักเขียนข้อมูลหรือไม่ D9 ถามการยอมรับช่วงหยุดตามนัดเมื่อวิธีดูแลระบบต้องใช้ ไม่ใช่การอนุญาตให้หยุดระบบจริงในขณะนี้

ความถี่สำรอง ระยะเก็บรักษา ปลายทางสำรอง ผู้รับผิดชอบจริง ระยะข้อมูลที่ยอมสูญเสียได้ และเวลาที่ต้องกู้คืนให้เสร็จ เป็นข้อกำหนดการดูแลที่ต้องยืนยันกับลูกค้าก่อนเปิด production แผนนี้ยังไม่สมมติตัวเลขหรือรับรอง SLA แทนลูกค้า

## ขั้นตอนอัปเดตและย้อนกลับที่ต้องอธิบายในคู่มือ

1. ยืนยันช่วงพักใช้งานนอกเวลาราชการกับผู้ดูแลลูกค้า พร้อมระบุผู้รับผิดชอบการตัดสินใจเปิดระบบอีกครั้ง
2. ให้ IT สำรองฐานข้อมูล รูป และ configuration/key ที่จำเป็นด้วยเครื่องมือของลูกค้า พร้อมระบุว่าชุดข้อมูลเหล่านี้สัมพันธ์กันอย่างไร
3. รอธุรกรรมที่กำลังทำงาน หยุดแอป/งาน cleanup ตามขั้นตอน แล้วใช้เฉพาะ migrations และชุดแอปที่ตรวจร่วมกันแล้ว
4. ตรวจว่าโฟลเดอร์ข้อมูลและ key ยังคงเดิม เริ่มแอปและตรวจฐานข้อมูล การล็อกอิน รูป และฟีเจอร์หลักก่อนเปิดรับงาน
5. หากต้องย้อนกลับ ให้ตรวจ compatibility ระหว่างแอปรุ่นเก่ากับ schema ก่อน การคืนแอปอย่างเดียวไม่ใช่การย้อน migration อัตโนมัติ และไม่ทับข้อมูลที่เกิดขึ้นใหม่ด้วย backup เก่าโดยไม่มีการพิจารณา

คู่มือเป็นสิ่งส่งมอบ ส่วนเครื่องมือสำรองจริงและตารางดูแลเป็นความรับผิดชอบ IT ตาม D8B

## ขอบเขตค่าตั้งที่เสนอ

ชื่อใหม่เป็นข้อเสนอสำหรับ implementation ไม่ใช่ตัวแปรที่มีอยู่แล้วทั้งหมด:

- เลือกรูปแบบติดตั้งและ provider ผ่านค่าตั้งฝั่ง server โดยเก็บฐานข้อมูลและข้อมูลรูปแยกกันระหว่าง cloud กับลูกค้า การเปลี่ยน provider ภายหลังที่มีข้อมูลต้องมีแผนย้ายเฉพาะ ไม่ใช่การเปลี่ยน flag แล้วคัดลอกข้อมูลให้อัตโนมัติ
- ใช้ค่าที่มีอยู่ `DATABASE_URL`, `BETTER_AUTH_URL`, `FRONTEND_URL`, `SMTP_*`, `BETTER_AUTH_SECRET` และ `TWO_FACTOR_ENCRYPTION_KEY` ต่อ ให้เป็นข้อมูลจริงของแต่ละการติดตั้ง
- เสนอ `IMAGE_STORAGE_PROVIDER=cloudinary|local` และ `IMAGE_STORAGE_ROOT` สำหรับ filesystem; ตัวตนของพื้นที่เก็บรูปต้องคงที่ข้ามการอัปเดต/รีสตาร์ต
- เสนอสวิตช์เปิดการพยากรณ์ที่มีค่าเริ่มต้นปิดในโหมดลูกค้า; การมี `GEMINI_API_KEY` เพียงอย่างเดียวไม่เปิดการส่งข้อมูลออกอัตโนมัติ
- ทีมติดตั้งจัดค่าบน server ตอน deploy และเริ่ม service ใหม่ตามขั้นตอน ไม่มีข้อกำหนดเพิ่มหน้าจอให้ผู้ใช้ตั้ง SMTP/API key ในงานนี้
- Frontend อ่านพฤติกรรมที่จำเป็นจากสัญญา API โดยไม่รับ secret หรือพาธจริงของ filesystem

## เกณฑ์ตรวจรับที่ต้องวางไว้ในงาน implementation

1. รูปแบบ cloud ยังอัปโหลด แสดงตัวอย่าง แนบ/เปลี่ยนรูป ลิงก์หมดอายุ และ cleanup ได้ตามสัญญาเดิม
2. รูปแบบลูกค้าใช้ฐานข้อมูลและไฟล์ในเครือข่ายที่กำหนด ปิด Gemini และตัดการออกอินเทอร์เน็ตสาธารณะแล้ว login/2FA และงานหลักผ่าน LAN ได้หลังเปิดบัญชี
3. เครือข่ายที่ตัดออกต้องไม่ถูกเข้าใจว่าทำให้ SMTP ภายนอกส่งได้ ทดสอบการส่งอีเมลแยกบนเส้นทางที่ลูกค้าอนุญาต
4. ต้นฉบับที่เกินขนาด/ชนิดหรือ decode ไม่สำเร็จต้องไม่ผูกกับทะเบียน; normalization และ HEIC ผ่านกับชุด runtime ที่ใช้จริง
5. รูปครุภัณฑ์มี URL version ที่เปลี่ยนเมื่อเปลี่ยนรูป รูปประจำบุคลากรไม่เป็น static public file ถาวร และคำขออ่านใหม่จากลิงก์ที่หมดอายุต้องถูกปฏิเสธ
6. การบันทึกที่ล้มเหลวหรือ response สูญหายไม่ทำให้รูปปัจจุบันหาย; cleanup ไม่ลบรูปที่ยังถูกอ้างอิง
7. proxy คง session cookie/CSRF และ notification SSE; หน้าเว็บและ font โหลดได้โดยไม่ต้องเรียก Google Fonts
8. fresh installation มีเฉพาะข้อมูลอ้างอิงและข้อมูลจริงที่เตรียม ไม่ปน demo users/assets และผ่าน handover check ของ ADMIN
9. restart/upgrade คงรูป ฐานข้อมูล secret และ key; แผน rollback ไม่ทับข้อมูลจริงด้วยโค้ด/ไฟล์จากรุ่นเก่าอย่างไม่ตรวจ compatibility
10. คู่มือ backup/restore ระบุการคืนชุดฐานข้อมูล+รูป+configuration/key ที่ต้องใช้ในปลายทางทดสอบแยก และเกณฑ์ตรวจการล็อกอิน/รูป IT ใช้เครื่องมือที่เลือกเพื่อทดลองขั้นตอนก่อนเปิด production; ทีมพัฒนาไม่สร้างเครื่องมือสำรองใหม่ตาม D8B

เกณฑ์นี้เป็นสิ่งที่จะตรวจเมื่อได้รับการยืนยันให้ implementation ยังไม่ได้รันทดสอบหรือเปลี่ยนโค้ดแอปในการสัมภาษณ์

## การยืนยันว่า Deploy ได้จริงหลังแก้โค้ด

ผู้ใช้ต้องการหลักฐานว่าระบบทำงานได้หลัง deploy จึงเพิ่ม [แผนซ้อม deploy และตรวจความพร้อม](customer-server-deployment-rehearsal.md) เป็นส่วนหนึ่งของการตรวจรับ: ตรวจโค้ด/ฐานข้อมูลทดสอบ → ซ้อมติดตั้งชุด production บน Ubuntu Server VM หรือเครื่องสะอาดที่ตรงรุ่น/สถาปัตยกรรม → ตรวจบน server ลูกค้าจากอีกเครื่องใน LAN ก่อนเปิดจริง

ต้องใช้ชุด release และค่าตั้งแบบเดียวกับที่ส่งมอบ ครอบคลุม HTTPS/session/2FA, SMTP, รูปและ HEIC, การตัดอินเทอร์เน็ตโดยคง LAN, การเริ่มหลัง reboot และการอัปเดตที่รักษาข้อมูลไว้ การผ่านเฉพาะ build หรือชุด tests ที่ใช้ auth/storage จำลองไม่ใช่หลักฐานว่า deploy สำเร็จครบถ้วน

ก่อนรันทดสอบรวมต้องตรวจและบังคับการใช้ฐานข้อมูลทดสอบทุกทาง ไม่สมมติว่าคำสั่ง test ทั่วไปแยกจากฐานจริงให้อัตโนมัติ และบันทึกสภาพแวดล้อม/ผลที่รันจริงต่อชุด release ส่วนเครื่องมือ backup ยังคงเป็นของ IT ตาม D8B

งานแพ็กสำหรับ P7 ต้องแยกสิ่งที่แอปใช้ตอนรันกับเครื่องมือ migrate/seed/bootstrap/handover ให้ชัด ปัจจุบัน Prisma CLI, tsx และ sharp อยู่ใน devDependencies และยังต้องรวม generated Prisma client/ไฟล์ decoder ให้ครบ การซ้อมบน Ubuntu Server ที่สะอาดต้องพิสูจน์ว่าขั้นตอนส่งมอบทำได้จากชุดที่เตรียมไว้จริง

## ข้อมูลสภาพแวดล้อมที่ขอภายหลังได้

ข้อมูลเหล่านี้ยังไม่ทราบ ไม่ใช่คำถามให้ผู้ใช้เดาเพื่อเริ่มวางแผนส่วนแอป:

- Ubuntu Server รุ่น เวอร์ชัน/build และสถาปัตยกรรมของเครื่องลูกค้า
- สถานะ OpenSSH, SSH port/เครือข่ายต้นทางที่อนุญาต, สิทธิ์ sudo และข้อจำกัด package repository หรือการติดตั้งแบบ offline
- CPU, RAM, พื้นที่เก็บข้อมูล และตำแหน่งที่อนุญาตให้ service เขียนไฟล์
- สิทธิ์ติดตั้งโปรแกรม/ลงทะเบียน service และการใช้เครื่องเสมือน
- URL ที่ผู้ใช้เปิด DNS HTTPS และข้อกำหนดเครือข่าย
- ปลายทาง SMTP ที่ลูกค้าอนุญาตและเงื่อนไขการส่งจริง รวมถึงนโยบายใช้บริการภายนอกและ Gemini โดยคงการเปิดบัญชีด้วยอีเมลตาม D4

ใช้ข้อมูลนี้สรุปวิธีติดตั้งและตรวจความเข้ากันได้ก่อน deploy จริง

## ขอบเขตการทำงานใน repository ระหว่างวางแผน

[CLAUDE.md](../../CLAUDE.md) อนุญาตให้อ่าน backend เพื่อวิเคราะห์ และให้เขียนเอกสารที่ repo root เมื่อได้รับคำขอ แต่ห้ามแก้ไฟล์ใต้ `backend/` ตามคำแนะนำปัจจุบัน จึงเก็บร่างแผนนี้ใน `docs/plans/` ที่ root การวางแผนยังระบุการเปลี่ยน backend ที่จำเป็นได้โดยอ้างอิงโค้ดเดิม

การสัมภาษณ์ใช้ทักษะ `grilling` และ `domain-modeling`: บันทึกคำตอบและคำศัพท์ที่ตกลงระหว่างทาง สร้าง ADR เมื่อมีการตัดสินใจที่มี trade-off และกลับลำยาก และให้ผู้ใช้ยืนยันความเข้าใจร่วมกันก่อนลงมือเปลี่ยนโค้ด
