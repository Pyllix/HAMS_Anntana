# Ticket 08 API contract

Ticket 08 BE/API scope is complete. This contract is ready for Ticket 09 to connect; FE wiring, refresh behavior, and browser verification remain in that ticket. See [ticket-08-performance-results.md](ticket-08-performance-results.md) for endpoint tests, lookup decisions, metrics, and measurement limits.

All list filters below apply before both page selection and `meta.total`. List endpoints retain the existing `{ data, meta }` pagination shape and stable ordering. Summary endpoints read matching rows from the database and are independent of page number and page size.

| Area | List API and filters | Summary / lookup API | Scope and count semantics |
|---|---|---|---|
| Borrow and return | `GET /borrowings?page&limit&statusCodes&sectionId` | `GET /borrowings/summary?sectionId` | Department staff are constrained to their own borrower section even if they submit another `sectionId`. Summary returns `total`, `byStatusCode`, and `overdueCount`; the history “pending” card is `PENDING_APPROVE + APPROVED` only. The API returns the real `PENDING_APPROVE` code and never manufactures `PENDING_APPROVAL`. |
| Assets | `GET /asset` and `GET /asset/my-section`, with `assetStatusCode`, `availabilityStatusCode`, and explicit-offset `updatedAtFrom` / `updatedAtTo` filters | `GET /asset/summary?section_id`; `GET /asset/my-section/summary` | Department staff using the global summary route are constrained to their own section, regardless of a requested section. Asset cards count each asset once by physical and availability status; null availability is returned as `UNASSIGNED`. Date filters use `updatedAt` and require an RFC 3339 timezone offset. |
| Repairs | `GET /repairs?page&limit&statusCodes&evaluatedOnly&workflowStep&stepActionType&hasPendingSparepartWithdrawal&sparepartSource&isRejected` plus existing status, action, urgency, date, mechanic, asset, reporter, and search filters | `GET /repairs/summary?sectionId&evaluatedOnly`; `GET /repairs/mechanic-workloads` | Department staff are constrained to their own repair section. `sparepartSource` accepts `ALL`, `INTERNAL`, `EXTERNAL`, or `MIXED`; it inspects only `PENDING_WITHDRAW` transactions before pagination. `workflowStep` uses the highest completed step, including later completed steps of another action type. Repair summaries count each job once, not once per mechanic or step. |
| Spare-part stock and selection | `GET /spare-parts?page&limit&search&groupId&stockStatus&lowStock`, where `stockStatus` is `NORMAL`, `LOW`, or `OUT` | `GET /spare-parts/summary`; `GET /spare-parts/:id` | Summary counts part types: NORMAL means stock above minimum, LOW means positive stock at or below minimum, OUT means zero or negative. Search/page/read-by-ID supports selecting an item beyond the first 100 results. |
| Stock-in history | `GET /spare-parts/stock-in-history?page&limit&search&sparepartAddDoc&sparepartId&addBy&startDate&endDate` | — | Existing Ticket 05/07 database-filtered history contract; deleted rows are excluded and the response retains exact pagination metadata. |
| User management | `GET /users?page&limit&search&role&section_id&banned` | — | Search, role, section, and active/banned filters are applied before pagination. `banned=false` includes both `false` and legacy `null` accounts. |

The current PostgreSQL endpoint tests verify the counted totals against seeded records beyond 100, status/source filters before pagination, cross-section protection on summaries, stable page traversal, and selected spare-part lookup by ID. The test suite is not a browser test; Ticket 09 still needs to wire these contracts into each table/card and verify all embedded and direct routes.
