# แผนข้อเสนอแนะระบบแจ้งเตือนทางอีเมลสำหรับระบบ HAMS (Email Notification Proposals)

เอกสารนี้รวบรวมและวิเคราะห์กรณีการใช้งาน (Use Cases) ที่เหมาะสมสำหรับการส่ง **Email Notification** เพิ่มเติมในระบบบริหารจัดการครุภัณฑ์โรงพยาบาล (HAMS) เพื่อใช้ประกอบการพิจารณาพัฒนาในอนาคต โดยคำนึงถึงความสมดุลระหว่างการรับรู้ข้อมูลที่สำคัญกับการป้องกันปัญหา **Email Fatigue** (การส่งอีเมลถี่เกินไปจนผู้ใช้ไม่อ่าน)

---

## 1. ปรัชญาการออกแบบการแจ้งเตือน (Notification Philosophy)

| ช่องทาง | บริบทการใช้งาน | ตัวอย่างเหตุการณ์ |
| :--- | :--- | :--- |
| **In-App Notification**<br>*(กระดิ่ง, Badge, Toast)* | ข้อมูลการดำเนินงานประจำวัน (Daily Micro-updates) ที่ผู้ใช้ล็อกอินเข้ามาทำงานแล้วควรเห็น | • มีผู้ขอยืมครุภัณฑ์<br>• ช่างรับงานซ่อมแล้ว / กำลังตรวจเช็ค<br>• มีการแก้ไขข้อมูลครุภัณฑ์ทั่วไป |
| **Email Notification**<br>*(จดหมายอิเล็กทรอนิกส์)* | เรื่องความปลอดภัย, เหตุการณ์ฉุกเฉิน/วิกฤต, การเตือนกำหนดเวลาที่ผู้ใช้ไม่ได้เปิดเว็บอยู่, และการขออนุมัติระดับบริหาร | • ยืนยันอีเมล / รีเซ็ตรหัสผ่าน<br>• เครื่องมือแพทย์ช่วยชีวิตชำรุดด่วน<br>• ครุภัณฑ์ซ่อมเสร็จพร้อมส่งคืน<br>• การยืมเลยกำหนดคืน<br>• ถึงรอบสอบเทียบ (Calibration / PM) |

---

## 2. สรุปรายการแจ้งเตือนตามลำดับความสำคัญ (Prioritized Notification Matrix)

| ระดับความสำคัญ | รายการแจ้งเตือน | ผู้รับ (Recipient) | ประโยชน์หลัก |
| :---: | :--- | :--- | :--- |
| **Priority 1**<br>*(Critical / Essential)* | 1. **Email Verification** | ผู้ใช้ที่เพิ่งสร้างบัญชี | ความปลอดภัยและการยืนยันตัวตน *(ดำเนินการแล้ว ✅)* |
| | 2. **Password Reset (ลืมรหัสผ่าน)** | เจ้าของบัญชีที่ร้องขอ | ฟังก์ชันความปลอดภัยพื้นฐานที่ผู้ใช้บริการตนเองได้ |
| | 3. **Emergency Repair (แจ้งซ่อมวิกฤต)** | หัวหน้าฝ่ายช่าง / ทีมช่างประจำวัน | เข้าระงับเหตุและซ่อมเครื่องมือช่วยชีวิตได้ทันท่วงที |
| **Priority 2**<br>*(High Value Operations)* | 4. **Repair Completed (ซ่อมเสร็จสิ้น)** | ผู้แจ้งซ่อม / แผนกเจ้าของเครื่อง | ลดการโทรตามงาน, นัดรับเครื่องกลับไปใช้กับคนไข้ |
| | 5. **Overdue Borrow (ยืมเลยกำหนดคืน)** | ผู้ยืม และหัวหน้าแผนกผู้ยืม | ติดตามครุภัณฑ์หมุนเวียนกลับสู่ระบบ |
| | 6. **PM & Calibration Due (เตือนรอบสอบเทียบ)** | เจ้าหน้าที่ศูนย์ครุภัณฑ์ / ช่างชีวการแพทย์ | รักษามาตรฐานโรงพยาบาล (HA/JCI) ความปลอดภัยของคนไข้ |
| **Priority 3**<br>*(Management Approval)* | 7. **Asset Disposal Approval (ขออนุมัติจำหน่าย)** | ผู้บริหาร (Manager / Director) | อนุมัติแทงจำหน่ายครุภัณฑ์มูลค่าสูงได้ทันเวลา |
| | 8. **High-Cost Repair Approval (อนุมัติซ่อมราคาสูง)** | ฝ่ายพัสดุ / ผู้บริหาร | อนุมัติงบประมาณและเบิกจ่ายอะไหล่ราคาแพง |

## 3. รายละเอียดเชิงลึกของแต่ละ Use Case (Detailed Specifications)

### 3.1 [Priority 1] การรีเซ็ตรหัสผ่าน (Password Reset / Forgot Password)
* **Trigger**: ผู้ใช้กด "ลืมรหัสผ่าน" ที่หน้าล็อกอิน หรือผู้ดูแลระบบสั่งส่งลิงก์รีเซ็ตรหัสผ่านให้ผู้ใช้
* **ผู้รับ**: อีเมลของผู้ใช้งาน
* **เนื้อหาสำคัญ**:
  * ลิงก์สำหรับตั้งรหัสผ่านใหม่ (เช่น Token มีอายุ 15-30 นาที)
  * ข้อมูลความปลอดภัย: IP Address, เบราว์เซอร์ที่ทำการร้องขอ
  * คำเตือน: *"หากคุณไม่ได้เป็นผู้ร้องขอ กรุณาละเว้นอีเมลนี้และติดต่อผู้ดูแลระบบ"*
* **ความคุ้มค่า**: จำเป็นอย่างยิ่งในการลดภาระ Helpdesk ที่แอดมินต้องคอยแก้รหัสผ่านให้ผู้ใช้

---

### 3.2 [Priority 1] แจ้งซ่อมเครื่องมือแพทย์วิกฤตฉุกเฉิน (Emergency / High-Risk Repair Alert)
* **Trigger**: แผนกผู้ป่วยวิกฤต (ICU, ER, ห้องผ่าตัด) แจ้งซ่อมครุภัณฑ์ที่มี `riskLevel: HIGH` หรือเลือกความเร่งด่วนระดับ "ฉุกเฉิน"
* **ผู้รับ**: หัวหน้างานซ่อมบำรุง (`MAINTENANCE_HEAD`) และอีเมลกลางของหน่วยงานวิศวกรรมการแพทย์
* **เนื้อหาสำคัญ**:
  * แผนกที่แจ้ง (เช่น ICU ชั้น 4)
  * ชื่อและหมายเลขครุภัณฑ์ (เช่น เครื่องช่วยหายใจ Hamilton-G5)
  * อาการชำรุด และเบอร์โทรติดต่อภายในของแผนก
  * ปุ่ม: *"ดูใบแจ้งซ่อมและมอบหมายงานทันที"*
* **ความคุ้มค่า**: ตอบสนองต่อภาวะวิกฤตของคนไข้ได้ทันท่วงที แม้ช่างไม่ได้นั่งหน้าคอมพิวเตอร์

---

### 3.3 [Priority 2] ซ่อมเสร็จสิ้น พร้อมส่งมอบคืน (Repair Completed & Ready for Pickup)
* **Trigger**: ช่างเปลี่ยนสถานะใบงานซ่อมเป็น `REPAIRED` (ซ่อมเสร็จสิ้นสมบูรณ์)
* **ผู้รับ**: ผู้แจ้งซ่อม (Reporter)
* **เนื้อหาสำคัญ**:
  * เลขที่ใบแจ้งซ่อม (Job No.) และชื่อครุภัณฑ์
  * สรุปผลการซ่อมแซม (เช่น เปลี่ยนสายสัญญาณ, ตรวจสอบ Safety ผ่านเกณฑ์)
  * ช่างผู้รับผิดชอบ และสถานที่ติดต่อรับเครื่องคืน (เช่น แผนกช่าง อาคารสนับสนุน ชั้น B1)
  * ปุ่ม: *"ตรวจสอบรายละเอียดและกดตรวจรับงานในระบบ"*
* **ความคุ้มค่า**: ลดภาระงานโทรศัพท์สอบถามของฝ่ายช่าง แผนกต้นทางนำเครื่องกลับไปใช้ดูแลคนไข้ได้เร็วขึ้น

---

### 3.4 [Priority 2] แจ้งเตือนการยืมครุภัณฑ์เลยกำหนดคืน (Overdue Borrow Alert)
* **Trigger**: ระบบ Cron Job ตรวจสอบทุกเช้า (เช่น 08:00 น.) พบว่ามีรายการยืมที่ `expectedReturnDate < NOW()` และยังไม่คืน
* **ผู้รับ**: ผู้ยืม (Borrower) และ CC หัวหน้าแผนกของผู้ยืม (เมื่อเลยกำหนดเกิน 3 วัน)
* **ความถี่**: แจ้งเตือนวันที่ 1, 3, และ 7 หลังเลยกำหนด
* **เนื้อหาสำคัญ**:
  * หมายเลขใบยืม (Borrow No.) และชื่อครุภัณฑ์
  * กำหนดส่งคืนเดิมที่เลยกำหนด
  * ปุ่ม: *"กดขยายเวลายืม (Request Extension)"* หรือ *"ขั้นตอนการส่งคืน"*
* **ความคุ้มค่า**: ป้องกันปัญหาครุภัณฑ์สูญหาย หรือถูกดองไว้ที่แผนกใดแผนกหนึ่งจนแผนกอื่นขาดแคลน

---

### 3.5 [Priority 2] แจ้งเตือนรอบสอบเทียบและบำรุงรักษาเชิงป้องกัน (PM & Calibration Due)
* **Trigger**: ระบบ Cron Job รันทุกต้นสัปดาห์ ตรวจจับครุภัณฑ์ที่ใกล้ถึงรอบ `nextPmDate` หรือ `nextCalDate` (ล่วงหน้า 30 วัน และ 15 วัน)
* **ผู้รับ**: เจ้าหน้าที่ศูนย์ครุภัณฑ์ (`ASSET_CENTER_STAFF`) หรือช่างชีวการแพทย์ (`MAINTENANCE_STAFF`)
* **เนื้อหาสำคัญ**:
  * สรุปรายชื่อครุภัณฑ์ที่จะหมดอายุการสอบเทียบในรอบเดือนนี้
  * แผนกที่ครุภัณฑ์ประจำการอยู่
  * ลิงก์ดาวน์โหลดรายงานแผนการสอบเทียบประจำเดือน
* **ความคุ้มค่า**: มีความสำคัญสูงสุดต่อการผ่านเกณฑ์มาตรฐานโรงพยาบาล (HA / JCI) ด้านความปลอดภัยของอุปกรณ์ทางการแพทย์

---

### 3.6 [Priority 3] ขออนุมัติแทงจำหน่ายครุภัณฑ์มูลค่าสูง (Asset Disposal Approval)
* **Trigger**: มีการสร้างเรื่องขอแทงจำหน่ายครุภัณฑ์ที่ราคาซื้อเดิมเกินเกณฑ์ (เช่น เกิน 100,000 บาท)
* **ผู้รับ**: ผู้อำนวยการ / ผู้บริหารฝ่ายบริหาร (`MANAGER`)
* **เนื้อหาสำคัญ**:
  * ข้อมูลครุภัณฑ์, อายุการใช้งาน, เหตุผลในการจำหน่าย (ชำรุดซ่อมไม่คุ้ม / ตกรุ่น)
  * สรุปความเห็นทางเทคนิคจากฝ่ายช่าง
  * ปุ่ม: *"เข้าสู่ระบบเพื่อพิจารณาอนุมัติ"*
* **ความคุ้มค่า**: ผู้บริหารสามารถเปิดอ่านสรุปจากอีเมลบนมือถือและคลิกเข้ามาอนุมัติในระบบได้โดยไม่ต้องรอเปิดคอมพิวเตอร์

---

## 4. สิ่งที่ไม่แนะนำให้ส่งทางอีเมล (Anti-Patterns to Avoid)

เพื่อรักษาให้กล่องข้อความอีเมลมีเฉพาะเรื่องสำคัญ ควรหลีกเลี่ยงการส่งอีเมลในกรณีต่อไปนี้ (ให้ใช้ In-App Notification แทน):

1. **การอนุมัติการยืมทั่วไปตามปกติ**: ไม่จำเป็นต้องส่งเมลทุกครั้งที่มีคนกดขอยืมหรืออนุมัติยืม
2. **ขั้นตอนย่อยของการซ่อม**: เช่น *"ช่างรับเรื่องแล้ว"*, *"กำลังตรวจสอบ"*, *"สั่งอะไหล่แล้ว"* ส่งเฉพาะตอนซ่อมเสร็จจุดเดียวพอ
3. **การแก้ไขข้อมูลครุภัณฑ์ทั่วไป**: เช่น เปลี่ยนรูปภาพ, แก้ไขชื่อรุ่น, เปลี่ยนยี่ห้อ

## 5. สถาปัตยกรรมทางเทคนิคสำหรับการต่อยอด (Technical Roadmap)

1. **Email Service Foundation**:
   * โครงสร้าง [src/common/mail/mail.service.ts](file:///f:/BUU/HAMS/HAMS_Anntana/backend/src/common/mail/mail.service.ts) ที่สร้างไว้ สามารถเพิ่ม Method ใหม่ได้ทันที เช่น:
     * `sendPasswordResetEmail(...)`
     * `sendRepairCompletedEmail(...)`
     * `sendOverdueBorrowEmail(...)`
2. **Scheduled Tasks (Cron Jobs)**:
   * ติดตั้ง `@nestjs/schedule` เพื่อรองรับการสแกนและส่งอีเมลแจ้งเตือนอัตโนมัติตามเวลา (เช่น Overdue Borrow และ PM/Calibration Due)
3. **User Notification Settings (ระยะยาว)**:
   * เพิ่มฟิลด์ใน User Profile ให้ผู้ใช้สามารถเลือกปิด/เปิดอีเมลแจ้งเตือนบางประเภทได้ตามความต้องการ (Opt-in / Opt-out)
