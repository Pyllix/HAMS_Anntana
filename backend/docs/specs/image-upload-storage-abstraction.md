## Confirmed delivery visibility

The confirmed policy distinguishes image purposes: asset images use stable versioned public CDN URLs without built-in expiry, while user profile photos require backend-authorized signed links expiring after five minutes. Anyone possessing an unexpired profile-photo link can view that photo without a HAMS session; this is an accepted exception, not a promise that outsider access is impossible or a legal classification of the data.

Authorizing an upload does not authorize or restrict subsequent image delivery. Cloudinary's authenticated delivery type does not itself validate a HAMS login session.

After discussing employee portraits, the user confirmed retaining restricted five-minute signed delivery for profile photos. Ordinary employee portraits must still be treated as personal data; the product's accepted sharing risk is not a legal finding that personal data may be published freely. The proposed one-day profile-photo cache header has not been confirmed or verified as supported by Cloudinary.

## Delivery decision and considered alternatives

How to enforce the delivery requirement while keeping Render usage manageable:

- Application-authorized issuance of a temporary provider download URL reduces backend image traffic, but anyone possessing that URL can use it until expiry. This does not strictly meet the outsider-access prohibition.
- A backend image endpoint can validate the current HAMS session and object-level read permission for each new request, then stream protected provider bytes without exposing or redirecting to a provider delivery URL. This adds backend bandwidth and availability/cold-start dependencies. It should prohibit shared/public caching and must never fetch an arbitrary client-supplied URL.
- CDN signed-cookie delivery keeps image bytes off Render and requires a separate browser credential, so sharing only the image URL does not grant access. The origin must remain protected against bypass. An issued cookie is a bearer credential valid until expiry; it is not automatically revoked by HAMS logout or role changes. Cloudinary requires Advanced or higher and an additional-cost custom delivery hostname for this approach.
- An independently authenticated edge delivery gateway is another architectural alternative: enforce image-read authorization outside Render and deliver protected origin bytes there. Provider, operating cost, session/revocation policy, and deployment complexity require separate evaluation; this is not an approved scope change.

The user rejected routing image bytes through Render and subsequently selected short-lived signed read URLs, later refining the decision to public CDN delivery for assets and signed read URLs for profile photos. Retain Cloudinary as the initial provider; no provider change is selected. For profile photos, the backend validates the current session and image-read permission before issuing each link, and the browser retrieves the image directly from Cloudinary. Logout and permission changes prevent future profile-photo link issuance, but do not automatically revoke an already-issued link. Asset-file delivery does not check the HAMS session. All approaches cannot revoke bytes already downloaded or prevent a viewer from copying an image.

Cloudinary profile-photo implementation constraint: a normal signed CDN delivery URL is not a time-limited read grant. The currently documented time-limited method is `private_download_url` with an explicit `expires_at`; it bypasses the CDN and costs twice the Cloudinary delivery bandwidth. The provider documentation discourages embedding this method on websites. This trade-off must remain visible in implementation/handoff notes and usage should be measured during trials; lower Render traffic does not imply zero cloud bandwidth cost. Do not substitute a permanent signed CDN URL while claiming profile-photo expiry. Protect both profile-photo originals and derivatives and avoid exposing permanent profile-photo delivery grants. Public asset images use the normal CDN path instead.

## Proposed HTTP cache policy

The earlier draft mentioned prohibiting shared/public caching only for the rejected backend-streaming alternative. It did not yet specify an HTTP cache contract for the selected direct-delivery design. Existing auth controller paths set `Cache-Control: no-store`, but there are no implemented image grant endpoints yet.

Recommendation awaiting confirmation:

- Backend responses containing upload authorization, short-lived read URLs, or provider credentials must use `Cache-Control: private, no-store`, including any future redirects and relevant authorization error responses. Apply the same policy to any user/asset/session response that embeds a temporary grant; do not inadvertently cache grants in another endpoint. `no-store` prohibits HTTP cache storage; `no-cache` alone permits storage with revalidation, and `private` alone still permits browser caching.
- The response serving actual image bytes belongs to Cloudinary, not HAMS. Headers on the grant API or redirect do not control that separate response. Cloudinary documents that `private_download_url` bypasses its CDN, but this is not proof of a browser `Cache-Control: no-store` header. Inspect actual provider headers during account-backed integration verification before declaring the image cache behavior. Do not assume arbitrary provider header overrides are supported on this delivery method.
- Signed URL validity and HTTP cache freshness are separate. A five-minute grant prevents new successful origin requests after expiry; it does not delete cached bytes, erase an already displayed image, or force a new request. Do not add an unconditional `public`, `immutable`, or `max-age=300` policy and mistake it for grant expiry enforcement.
- Frontend application-memory caching is separate from HTTP caching. If used, scope grants to the current user/session and image identity/version, do not reuse them after `expiresAt`, and clear them on logout/account switch and image replacement. Do not persist signed grants in localStorage, persisted query caches, service-worker caches, or database fields. Refresh only when necessary; do not re-download a displayed image on a five-minute timer.

Verification to include in the BE-first handoff: assert grant and embedded-grant response headers; ensure grants cannot be shared through application/server cache keys; observe Cloudinary image success/error headers; and prove that a new cache-bypassed provider request fails after expiry while documenting that already downloaded bytes may remain visible. This does not route image bytes through Render.

### User's alternative under discussion

A successfully uploaded verified pending image may be reused for an authorized save retry within its one-hour window, and an unused expired image becomes eligible for bounded cleanup. Account creation without an employee photo remains permitted. None of these rules authorizes silently clearing an existing attachment.

Actionable error wording, preservation of unsaved form inputs, retry controls, and cancellation of a pending selection are frontend implementation/handoff details under these constraints, not a new approval gate for the same lifecycle policy. Cancelling a pending selection is distinct from the excluded standalone removal of an attached photo. Keep the save outcome explicit; do not present an unsuccessful intended image replacement as successful.

## Verified provider references

- [Cloudinary client-side uploading](https://cloudinary.com/documentation/client_side_uploading): signed browser uploads obtain the signature from the backend and send image bytes directly to Cloudinary.
- [Cloudinary access control](https://cloudinary.com/documentation/control_access_to_media): authenticated delivery protects originals and derived assets; signed delivery URLs and time-limited download URLs are distinct. Time-limited download URLs bypass the CDN and incur twice the bandwidth. Token/cookie-based CDN access is an Advanced-plan-or-higher feature.
- [CloudFront signed cookies](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-signed-cookies.html): an application issues authorization cookies and the CDN validates them when delivering restricted content. This is an example of the credential-gated CDN pattern, not a selected provider.
- [Cloudinary authentication signatures](https://cloudinary.com/documentation/authentication_signatures): upload signatures are valid for one hour from their timestamp. Application upload-session expiry must not be mistaken for Cloudinary signature expiry.
- [Cloudinary upload responses](https://cloudinary.com/documentation/upload_images): upload responses include provider identifiers, version, dimensions, format, and a verification signature. Client-supplied URLs alone are insufficient proof of a valid application upload.
- [HTTP Cache-Control semantics](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control): `no-store`, `no-cache`, and `private` have distinct effects; HTTP caching does not revoke already downloaded content.
- [Cloudinary supported image formats](https://cloudinary.com/documentation/image_format_support): HEIF (`.heif`, `.heic`) supports image uploads and transformations, including conversion to a different display format.
- [Cloudinary incoming transformations](https://cloudinary.com/documentation/eager_and_incoming_transformations): incoming transformations modify an image before storage; unlike eager derivatives they do not preserve an additional unchanged original. Do not use `f_auto` as an incoming transformation.
- [Cloudinary transformation counts](https://cloudinary.com/documentation/transformation_counts): upload processing counts as one transformation with or without incoming transformations; additional generated derivatives have their own counts, while requests for an already generated identical transformation do not add processing counts.
- [Cloudinary billing and plans](https://cloudinary.com/documentation/billing_and_plans): standard credits combine transformation, storage, and bandwidth usage; one credit covers 1,000 standard transformations, not an unlimited number of image deliveries.
- [Cloudinary plan limits](https://cloudinary.com/pricing/compare-plans): the published Free-plan image file ceiling is 10 MB; account-backed verification must still check the actual account configuration and image-processing limits.
- [Cloudinary quality settings](https://cloudinary.com/documentation/image_optimization): a numeric quality setting between 1 and 100 controls the compression/visual-quality trade-off; it is not a fixed percentage of retained detail or resulting file size.
- [Cloudinary background parameters](https://cloudinary.com/documentation/transformation_reference#b_background) and [transformation rules](https://cloudinary.com/documentation/cloudinary_transformation_rules): background colors can fill transparent areas; in chained transformations use a suitable dimension-preserving pad qualifier when needed rather than relying on an isolated background component.
- [Cloudinary incoming metadata stripping](https://cloudinary.com/documentation/transformation_reference#fl_force_strip) and [metadata optimization](https://cloudinary.com/documentation/image_optimization): explicitly use `fl_force_strip` during incoming transformations to remove embedded source metadata; standardized `DigitalSourceType` information is preserved even with that flag.
- [Render Free service behavior](https://render.com/docs/free): Free web services spin down after 15 minutes without incoming traffic and resume on a subsequent request; an in-process cleanup task cannot execute while the service is suspended. This is provider documentation, not an inspection of the customer's deployment settings.

- Start with Cloudinary behind a replaceable storage abstraction.

- Defer wait-disposal changes and related repair/custody corrections for separate team discussion; focus this phase on main asset CRUD images and ADMIN-managed employee photos.

- Asset images use stable versioned public CDN URLs: anyone with the URL may view them without a HAMS session or built-in link expiry. User profile photos remain restricted, including the accepted risk that an outsider holding a still-valid signed link can view the photo.
- Do not route image file delivery through Render; the user wants to avoid its additional image bandwidth. Small authorization/API responses are distinct from file delivery traffic.
- Use backend-authorized short-lived signed read URLs and direct Cloudinary delivery for profile photos; already-issued links remain usable until their expiry even after logout.
- Profile-photo read links expire five minutes after issuance; keep the lifetime configurable. Public profile-photo delivery is not selected.
- Any authenticated HAMS user passing the existing access guards may obtain an attached employee-photo read link, including for another employee; grant issuance is not restricted to the owner or ADMIN. Photo mutations remain ADMIN-only, and UI visibility is not an authorization boundary.
- No automated or manual image-content review/approval is included; removing content checks does not remove technical file validation or upload authorization.
- Employee photos are managed by ADMIN, normally added before account handover. Employees cannot upload or change their own photo; employee-photo upload authorization and attachment mutations must enforce ADMIN permission in the backend.
- Reuse existing RBAC; do not introduce a separate image permissions system or broaden feature mutation rights. New image endpoints must participate in the existing guards and appropriate purpose-specific feature policy.
- Account creation does not require an employee photo. ADMIN can create the account first and add the photograph later; no new mandatory-photo or handover gate is included.
- One main image per asset, replaceable through the existing CRUD edit/save flow; no gallery or separate image-editing workflow is included. Cancelling or failing a save must preserve the current attached image.
- Exclude standalone removal of main asset images and employee photos. Support no initial image, adding, and replacing; do not add remove buttons/endpoints or silently clear existing attachments through empty/null updates.
- Accept HEIC/HEIF photos and convert/resize them to JPEG during direct upload using provider incoming transformations; do not retain the unchanged HEIC source alongside a JPEG derivative. Source pixel limits remain unresolved.
- Use the same configurable 10 MB (10,000,000 bytes) source-file ceiling for main asset images and employee photos, within provider limits; resizing does not change this source-file policy.
- Store images with a longest-edge cap of 1,600 pixels for main asset images and 512 pixels for employee photos; preserve aspect ratio without cropping/upscaling and do not retain a full-resolution original alongside the resized result.
- Use configurable JPEG encoder quality 80 for both image purposes; this is not an automatic-quality policy or a guaranteed visual-fidelity/file-size percentage.
- Normalize every accepted image input to one stored JPEG, flattening existing transparency onto white through Cloudinary incoming processing; do not remove opaque photographic backgrounds or retain an extra source-format copy.
- Apply source orientation and remove unnecessary embedded metadata, including GPS/camera/capture details, during Cloudinary incoming processing for both image purposes. Verify the output rather than assume JPEG conversion strips metadata; do not promise removal of provider-preserved standardized provenance tags.
- Do not retain superseded image files as history. Delete the unreferenced old cloud object only after a successful replacement commit, and persist failed cleanup for safe retry without undoing the saved edit.
- Keep uploaded but unattached images in Cloudinary for a configurable one-hour attachment window, superseding the earlier 24-hour decision, with tracking metadata in HAMS. After expiry reject attachment and make unreferenced files eligible for safe cleanup; attached images do not expire under this rule.
- Persist cleanup/retry work in the existing database and process bounded batches while BE is running, including on startup, without an additional paid worker/cron service. Physical deletion may be delayed beyond pending expiry while BE is asleep/offline or the provider is unavailable; exact scheduling and batch size remain technical design items.
- Use last-successful-save-wins for concurrent image replacements without stale-photo conflict dialogs or edit locks. Atomically track the actual superseded attachment for safe cleanup; image-omitting saves preserve the current image and cleanup must never delete a live attachment.
- Use record-level image URL plus minimal provider-file metadata rather than mandatory central image-ID attachment references. Assets persist stable versioned public URLs; employee photos persist provider-file references and generate expiring read URLs dynamically. Keep separate durable pending-upload/cleanup tracking and the requested Storage Abstraction; exact schema and response/session compatibility remain to be designed.

Image Base64 Data URLs, if found, are disposable test residue that may be cleared after exact target checks, without deleting business records, seed URL images, or unrelated data. Do not equate this with permission to discard future customer photos or change the deferred wait-disposal workflow.
