# แผนระบบ notification BE ผ่าน SSE สำหรับ HAMS

วันที่: 2026-10-13

สถานะ: แผนต้นทางที่แปลงเป็นสเปกแล้ว ยังไม่ได้แก้โค้ด runtime หรือสร้าง migration

สเปกหลักสำหรับพัฒนาอยู่ใน [local issue tracker](../../.scratch/in-app-notifications-sse/spec.md) สถานะ ready-for-agent ใช้สเปกนั้นเป็นข้อกำหนดหลัก โดยจุดทดสอบ API/SSE กับฐานข้อมูลทดสอบจริงได้รับการยืนยันแล้ว

## 1. ขอบเขตที่ตกลง

- ทำเฉพาะ notification ฝั่ง BE ใช้ SSE และเริ่มด้วย BE หนึ่ง instance
- ใช้ PostgreSQL/Prisma เดิม เพิ่มตาราง Notification เพียงตารางเดียว แยกแถวตามผู้รับและสถานะอ่านรายคน
- เก็บข้อความย้อนหลัง อ่านแล้วหรือรายการต้นทางจบแล้วก็เก็บแถวเดิม อ่านรายการแบบแบ่งหน้า ระยะแรกไม่มี archive หรือระบบลบตามอายุ
- ไม่มีงานแก้ FE, หน้าติดตามใหม่, การแก้ flow ยืม/ซ่อม หรือการเปลี่ยนความหมายกำหนดคืนเดิม
- ไม่เพิ่ม Redis, message broker, ตารางประวัติแยก หรือระบบติดตามสถานะงานซ้ำใน notification
- ไม่สร้างแจ้งเตือนเครื่องซ่อมไม่ได้รอพัสดุรับคืน เพราะช่างนำเครื่องไปส่งมอบจริงและมีขั้นพัสดุบันทึกรับคืนอยู่แล้ว
- หน่วยงานแจ้งซ่อมเฉพาะเครื่องของตน ศูนย์แจ้งซ่อมเฉพาะเครื่องส่วนกลางให้ยืม จึงใช้ RepairJob.sectionId เลือกสมาชิกหน่วยงานรับแจ้งซ่อมเสร็จ
- เอกสารนี้เป็นแผนปัจจุบันสำหรับงานนี้ ข้อเสนอ Polling ใน ../in_app_notification_architecture.md เป็นเอกสารเดิม

## 2. เหตุการณ์และผู้รับที่ยืนยันแล้ว

ผู้รับต้องเป็นบัญชีที่ยังใช้งานได้ ใช้กฎบัญชีเดิมของระบบในการตรวจบัญชีที่ลบ/ถูกระงับ กลุ่มผู้รับถูกเลือกตอนสร้างเหตุการณ์ ไม่จำกัดเฉพาะคนที่ออนไลน์

| Type                               | เกิดเมื่อ                                                 | ผู้รับ                                                                    |
| ---------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------- |
| BORROW_APPROVAL_REQUIRED           | สร้างคำขอยืมที่เข้า PENDING_APPROVE สำเร็จ                | ASSET_CENTER_STAFF ทุกคน                                                  |
| BORROW_APPROVED                    | คำขอยืมเปลี่ยนจาก PENDING_APPROVE เป็น APPROVED สำเร็จ    | ผู้ขอยืมของรายการนั้น (borrower_id) ตามขอบเขตแจ้งผลของ department ที่ตกลง |
| REPAIR_APPROVAL_REQUIRED           | งานถึงขั้นรอพัสดุอนุมัติเบิกอะไหล่หรือส่งซ่อมภายนอก       | PARCEL_STAFF ทุกคน                                                        |
| REPAIR_READY_FOR_COLLECTION        | ช่างทำขั้นแล้วเสร็จจนงานเข้า WAITING_DELIVERY สำเร็จ      | สมาชิกหน่วยงานของ RepairJob.sectionId ทุกคน                               |
| BORROW_EXTENSION_APPROVAL_REQUIRED | สร้างคำขอต่ออายุ ONLINE สถานะ PENDING สำเร็จ              | ASSET_CENTER_STAFF ทุกคน                                                  |
| BORROW_EXTENSION_APPROVED          | คำขอต่ออายุเปลี่ยน PENDING → APPROVED สำเร็จ              | ผู้ส่งคำขอต่ออายุ (requestedByUserId) คนเดียว                             |
| BORROW_EXTENSION_REJECTED          | คำขอต่ออายุเปลี่ยน PENDING → REJECTED สำเร็จ              | ผู้ส่งคำขอต่ออายุ (requestedByUserId) คนเดียว                             |
| BORROW_DUE_SOON                    | รายการ BORROWED ที่มีวันคืนเข้าในช่วง 24 ชั่วโมงก่อนกำหนด | ผู้ยืม (borrower_id) คนเดียว                                              |
| BORROW_OVERDUE                     | รายการ BORROWED ที่มีวันคืนเลยกำหนดที่บันทึก              | ผู้ยืม + ASSET_CENTER_STAFF ทุกคน                                         |

- พัสดุไม่มีแจ้งผลอนุมัติยืมตามการแก้ไขขอบเขตของผู้ใช้ ผลอนุมัติยืมในแผนนี้ใช้สำหรับผู้ขอที่เป็น department
- ใกล้คืนและเกินกำหนดส่งตามตัวผู้ยืมได้ รวมถึงผู้ยืมที่เป็นพัสดุ ไม่กระจายให้ทั้งแผนกผู้ยืม
- ถ้าคนเดียวกันอยู่ในหลายกลุ่มผู้รับ ให้รวมตาม userId และสร้างเพียงแถวเดียวต่อเหตุการณ์
- การอ่านแยกรายคน คนหนึ่งอ่านไม่ทำให้คนอื่นอ่านแล้ว และการอ่านไม่ถือว่าอนุมัติหรือทำงานเสร็จ
- Notification เก็บข้อความของเหตุการณ์ ณ เวลาที่เกิด สถานะงานปัจจุบันตรวจจาก API ยืม/ซ่อมเดิม

## 3. กฎเวลาและการป้องกันแจ้งซ้ำ

### กฎที่ยืนยัน

- ใช้ expectedReturnDate ที่บันทึกในฐานข้อมูล ไม่แปลงเป็นสิ้นวันและไม่แก้ FE
- เฉพาะสถานะ BORROWED หากแจ้งคืนแล้ว รอรับคืน คืนแล้ว หรือยกเลิก จะไม่สร้างแจ้งใกล้คืน/เกินกำหนดใหม่
- ถ้า expectedReturnDate เป็น null ให้ข้ามสองเหตุการณ์นี้ แจ้งเตือนเหตุการณ์อื่นยังทำงานตามปกติ
- ใกล้คืนเตือนหนึ่งครั้งล่วงหน้า 24 ชั่วโมง เกินกำหนดเตือนหนึ่งครั้งต่อกำหนดคืนที่มีผล
- อนุมัติต่ออายุแล้วจึงเริ่มรอบใหม่ตามวันคืนใหม่ คำขอต่ออายุที่ยัง PENDING ไม่เปลี่ยนวันคืนและไม่เริ่มรอบใหม่

### ข้อเสนอทางเทคนิค

- ตรวจทุก 1 นาทีด้วย @nestjs/schedule และตรวจรอบหนึ่งหลัง BE เริ่มทำงาน ไม่สร้าง timer แยกสำหรับทุกรายการยืม
- ใช้เวลาเดียวกันตลอดหนึ่งรอบตรวจ: ใกล้คืนเมื่อ now <= dueAt <= now + 24 ชั่วโมง; เกินกำหนดเมื่อ dueAt < now ให้ตรงกับเกณฑ์เกินกำหนดปัจจุบัน
- คัดรายการเป็นชุด อ่าน/ล็อกแถวรายการยืมและตรวจสถานะกับวันคืนล่าสุดอีกครั้งใน transaction ก่อนสร้าง เพื่อไม่แจ้งตามวันคืนเก่าขณะมีการคืนหรืออนุมัติต่ออายุพร้อมกัน
- รายการเริ่มยืมแล้วเหลือไม่ถึง 24 ชั่วโมงใช้เกณฑ์เดียวกัน: แจ้งใกล้คืนในรอบตรวจแรกที่เข้าเกณฑ์ ไม่เพิ่มประเภทยืมระยะสั้น
- ถ้าเริ่มตรวจตอนเกินกำหนดแล้ว สร้างเฉพาะเกินกำหนด ไม่ย้อนหลังไปสร้างใกล้คืนที่พลาด
- ป้องกัน job รันซ้อนภายใน instance และใช้ unique constraint เป็นด่านป้องกันข้อมูลซ้ำ
- eventKey ของแจ้งตามเวลาใช้ชนิดเหตุการณ์ + borrowId + expectedReturnDate ที่มีผล
- เมื่อมีแถวของ eventKey นั้นแล้ว ไม่เติมผู้รับใหม่ทุกครั้งที่ job ตรวจซ้ำ ไม่ทำให้เจ้าหน้าที่ที่เพิ่งเข้ากลุ่มได้รับเหตุการณ์เก่าซ้ำ
- แจ้งตามเวลาอาจช้ากว่าจุดเข้าเกณฑ์ได้ประมาณหนึ่งรอบตรวจเมื่อ BE ทำงานตามปกติ เหตุการณ์จากการกดอนุมัติ/ซ่อมส่งหลัง transaction สำเร็จทันที

Nest รองรับการตั้งงานตามเวลาผ่าน [@nestjs/schedule](https://docs.nestjs.com/techniques/task-scheduling) รายละเอียดข้างต้นเป็นรูปแบบที่เสนอให้ใช้กับ BE ตัวเดียวนี้

## 4. ตาราง Notification

แต่ละแถวคือแจ้งเตือนของผู้รับหนึ่งคน ใช้ตารางเดียวสำหรับข้อความย้อนหลังและสถานะอ่าน

| ฟิลด์ที่เสนอ              | หน้าที่                                                      |
| ------------------------- | ------------------------------------------------------------ |
| id                        | UUID ของแจ้งเตือน                                            |
| userId                    | ผู้รับ อ้างถึง User                                          |
| type                      | หนึ่งในเหตุการณ์จากตารางข้อ 2                                |
| title / message           | ข้อความที่สร้างโดย BE                                        |
| resourceType / resourceId | อ้างถึง BorrowTransaction, BorrowExtension หรือ RepairJob    |
| eventKey                  | รหัสเหตุการณ์สำหรับป้องกันสร้างซ้ำ                           |
| readAt                    | null เมื่อยังไม่อ่าน; timestamp เมื่อผู้รับทำเครื่องหมายอ่าน |
| createdAt                 | เวลาสร้างแจ้งเตือน                                           |

- unique: (eventKey, userId)
- index: (userId, readAt) และ (userId, createdAt, id)
- ดึงรายการเรียง createdAt DESC, id DESC เพื่อให้ลำดับแน่นอน
- เนื้อหาไม่เก็บข้อมูลยืม/งานซ่อมทั้งก้อน ไม่เพิ่ม status ล่าสุดของงานลงตารางนี้
- กรณีส่งทั้งกลุ่มใช้ createMany ภายใน transaction ที่สร้างเหตุการณ์เดียวกัน
- eventKey ของงานซ่อมใช้รหัสขั้น RepairJobStep เพื่อแยกขั้นที่สร้างใหม่หลังประเมินใหม่ออกจากเหตุการณ์เดิม

## 5. โมดูลและจุดเชื่อม BE

เสนอ NotificationsModule ประกอบด้วย controller, service, stream service, borrow reminder service และ DTO เท่าที่จำเป็น

- NotificationsService รับรายการผู้รับ/ชนิด/ข้อความ/รายการอ้างอิง และ Prisma transaction จาก service ต้นทาง บันทึกและกันข้อมูลซ้ำ
- NotificationStreamService ดูแล stream ตาม userId และหลาย connection ของผู้ใช้คนเดียวภายใน process
- BorrowReminderService ตรวจใกล้คืน/เกินกำหนดตามข้อ 3
- AssetBorrowModule และ RepairsModule เรียกผ่าน NotificationsService; ไม่ย้ายกฎธุรกิจยืม/ซ่อมมาไว้ใน controller notification

| จุดเชื่อมเดิม                      | สิ่งที่จะเพิ่ม                                                          |
| ---------------------------------- | ----------------------------------------------------------------------- |
| AssetBorrowService.createBorrow    | แจ้งศูนย์เฉพาะรายการที่เกิด PENDING_APPROVE                             |
| AssetBorrowService.approveBorrow   | แจ้งผลตามผู้รับ BORROW_APPROVED                                         |
| AssetBorrowService.createExtension | แจ้งศูนย์เฉพาะ ONLINE / PENDING                                         |
| AssetBorrowService.reviewExtension | แจ้งผู้ส่งคำขอเมื่ออนุมัติหรือปฏิเสธ                                    |
| RepairsService.diagnoseAndPlan     | หลังสร้างขั้นซ่อม ตรวจขั้นถัดไปที่รอพัสดุอนุมัติ WITH_PARTS / OUTSOURCE |
| RepairsService.updateStepProgress  | เมื่อเปลี่ยนเข้าสู่ WAITING_DELIVERY แจ้งหน่วยงานของงานซ่อม             |
| งานตรวจตามเวลา                     | แจ้งใกล้คืน/เกินกำหนดตามสถานะและวันคืนล่าสุด                            |

ใช้ขั้นที่รอดำเนินการและสิทธิ์ของขั้นสำหรับแจ้งรอพัสดุอนุมัติ ไม่ตรวจเฉพาะ PARCEL_PROCESSING เพราะ WITH_PARTS ที่มีอะไหล่นอกคลังอาจเป็น WAITING_PARTS แต่ยังรอพัสดุทำขั้นอนุมัติ

คำขอที่ศูนย์สร้างให้และอนุมัติ/ส่งมอบทันที (CENTER_SERVICE) ไม่เกิด PENDING_APPROVE จึงไม่สร้างแจ้งรออนุมัติหรือเพิ่มเหตุการณ์ผลอนุมัติอื่นนอกตาราง ส่วนการต่ออายุ DESK ที่อนุมัติทันทีไม่สร้างแจ้งรออนุมัติหรือผลของคำขอ PENDING

### ลำดับการบันทึกและส่ง

1. ตรวจเงื่อนไขและเปลี่ยนสถานะรายการต้นทางตาม flow เดิม
2. สร้าง Notification ของผู้รับใน Prisma transaction เดียวกับเหตุการณ์นั้น
3. transaction สำเร็จแล้วจึงส่ง SSE ให้ connection ของผู้รับ
4. rollback แล้วไม่เหลือ notification และไม่ส่ง SSE
5. การส่ง SSE ล้มเหลวหลัง commit ไม่ย้อน transaction ธุรกิจ ข้อมูลที่บันทึกยังอ่านจาก API ได้ ให้ปิด stream ที่ล้มเหลวเพื่อ reconnect และโหลดข้อมูลล่าสุด

ฐานข้อมูลเป็นแหล่งข้อมูลหลัก SSE เป็นช่องแจ้งข้อมูลใหม่ ไม่เก็บประวัติไว้ในหน่วยความจำ

## 6. API และสัญญา SSE

| Endpoint ที่เสนอ                   | ผลลัพธ์                                                                                                                                                                                                                                 |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET /notifications?page=1&limit=20 | รายการของผู้ใช้ปัจจุบันและ meta แบ่งหน้า; limit สูงสุด 100                                                                                                                                                                              |
| GET /notifications/unread-count    | จำนวนที่ยังไม่อ่านของผู้ใช้ปัจจุบัน                                                                                                                                                                                                     |
| PATCH /notifications/:id/read      | รับ body ว่าง; ตั้ง readAt เฉพาะแถวของผู้ใช้ปัจจุบันและคืน notification; อ่านซ้ำคืน readAt เดิม                                                                                                                                         |
| PATCH /notifications/read-all      | รับ body ว่าง; คืน `{ updatedCount, readAt }`; ใช้ cutoff ที่จับตอน handler เริ่มก่อน I/O และอ่านเฉพาะแถวที่ยังไม่อ่านซึ่ง `createdAt` ไม่เกิน cutoff; รายการใหม่หลัง cutoff ยังคงไม่อ่าน; เมื่อไม่มีแถวที่เปลี่ยน `readAt` เป็น `null` |
| GET /notifications/stream          | SSE ของผู้ใช้ปัจจุบัน                                                                                                                                                                                                                   |

- อ่าน userId จาก session ไม่รับผู้รับหรือ userId ของผู้อื่นจาก request
- ใช้ cookie authentication และ guards เดิม รวมถึง CSRF สำหรับ PATCH
- เข้าถึงแถวของผู้อื่นตอบ 404 ไม่เปิดเผยว่ามีแถวนั้นอยู่
- API อ่านและ SSE ไม่เปลี่ยนสถานะยืมหรืองานซ่อม
- ปฏิเสธ field ใน body ของ PATCH; ผู้เรียกกำหนด `userId`, `readAt` หรือข้อความเองไม่ได้
- `read-all` ใช้ timestamp เดียวกันเป็น readAt ให้ทุกแถวที่เปลี่ยน และส่ง invalidation หลัง commit เฉพาะเมื่อ `updatedCount` มากกว่า 0
- ส่ง field id, type, title, message, resourceType, resourceId, readAt, createdAt โดยไม่ต้องเปิดเผย eventKey หรือ userId ใน payload

เสนอใช้ @Sse และ RxJS ซึ่งโปรเจกต์มีอยู่แล้ว ตาม [เอกสาร SSE ของ Nest](https://docs.nestjs.com/techniques/server-sent-events) พร้อม cleanup subscription/timer เมื่อ connection ปิด

| --------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| notification.created        | มี notification ใหม่ ส่งข้อมูลแถวของผู้รับคนนั้น                                                                  |
| notifications.changed       | สถานะอ่านเปลี่ยน; ส่ง `{ "reason": "read_state" }` ให้ทุก connection ของผู้ใช้เดียวกันเพื่อโหลดรายการและจำนวนใหม่ |
| notifications.sync_required | ส่งเมื่อเชื่อมต่อหรือ reconnect เพื่อให้ผู้เรียกดึงรายการและจำนวนล่าสุดจาก API                                    |
| heartbeat                   | สัญญาณรักษาการเชื่อมต่อ ไม่ใช่ notification และไม่นับเป็นกิจกรรมของผู้ใช้                                         |

- ลงทะเบียน connection ก่อนส่ง sync_required เพื่อไม่ให้มีช่องว่างระหว่างเริ่มเชื่อมต่อกับการรับเหตุการณ์ใหม่
- heartbeat เสนอทุก 15 วินาที ตรวจ session ระหว่างรอและก่อนส่งข้อมูล โดยใช้กฎ SessionLifetimeService เดิมและไม่ต่ออายุ idle จาก heartbeat
- session หมดอายุ/ถูกเพิกถอนหรือบัญชีใช้งานไม่ได้ให้ปิด stream; ไม่รับ token ใน URL
- ส่งเฉพาะหลัง commit ตรวจการส่งหลายแท็บ/อุปกรณ์ของผู้ใช้เดียวกัน และไม่ส่งให้ผู้ใช้คนอื่น
- reconnect ใช้การดึงข้อมูลล่าสุด ไม่เพิ่มระบบ replay event log หรือรับประกันส่งทุก frame เพียงครั้งเดียว ผู้เรียกใช้ id กันรายการซ้ำ
- response ใช้ text/event-stream และตั้ง header ที่ป้องกัน cache/buffering ตามการรันจริง ตรวจ streaming ผ่าน proxy ที่มีอยู่
- งานนี้จัดทำสัญญาสำหรับการเชื่อมต่อเท่านั้น ไม่แก้ code FE

## 7. ลำดับพัฒนาและการตรวจรับ

| ลำดับ | งาน                                           | เกณฑ์เสร็จ                                                                   |
| ----- | --------------------------------------------- | ---------------------------------------------------------------------------- |
| 1     | เพิ่ม schema, migration และโมดูล notification | หนึ่งตาราง; unique/index ถูกต้อง; ไม่เปลี่ยนข้อมูลกำหนดคืนเดิม               |
| 2     | เพิ่ม API รายการ/จำนวน/อ่าน                   | ข้อมูลและสถานะอ่านแยกรายคน แบ่งหน้าและเรียกอ่านซ้ำได้                        |
| 3     | เชื่อมเหตุการณ์ยืม/ต่ออายุ/ซ่อม               | ผู้รับตรงตารางข้อ 2; บันทึกพร้อมเหตุการณ์และไม่สร้างซ้ำ                      |
| 4     | เพิ่ม SSE                                     | ผู้รับเห็นข้อมูลใหม่หลัง commit, cleanup ได้, session มีผลระหว่างเปิด stream |
| 5     | เพิ่มงานตรวจเวลา                              | ครอบคลุมช่วง 24 ชั่วโมง, เกินกำหนด, null, คืนแล้ว และต่ออายุ                 |
| 6     | ตรวจการทำงานรวมและเอกสาร API                  | กรณีสำคัญผ่านและยืนยันว่าไม่แก้ FE/flow เดิม                                 |

กรณีตรวจหลัก:

- ผู้รับงานรออนุมัติทั้งบทบาท, ผู้รับซ่อมเสร็จเฉพาะหน่วยงานของงาน, และผลต่ออายุเฉพาะ requestedByUserId ที่อาจต่างจาก borrower_id
- พัสดุไม่รับผลอนุมัติยืม และงาน UNREPAIRABLE ไม่สร้างแจ้งเตือนรับคืน
- อ่านรายการ/อ่านทั้งหมดของคนหนึ่งไม่เปลี่ยนของอีกคน และข้ามการเข้าถึง notification ของผู้อื่น
- ขอบเขต 24 ชั่วโมงและเลยกำหนดตรงกับเวลาในฐานข้อมูล ใช้นาฬิกาทดสอบที่ควบคุมได้
- null, สถานะก่อนส่งมอบ, แจ้งคืนแล้ว, คืนสำเร็จ และยกเลิก ไม่สร้างแจ้งตามเวลา
- ตรวจซ้ำ/รันซ้อน/รีสตาร์ตไม่ส่งเหตุการณ์เดิมซ้ำ; อนุมัติต่ออายุใช้กำหนดใหม่และ PENDING ใช้กำหนดเดิม
- คืนหรือต่ออายุพร้อมกับรอบตรวจ ไม่สร้างแจ้งตามข้อมูลที่เปลี่ยนไปแล้ว
- transaction rollback ไม่เกิด notification/SSE; offline/reconnect อ่านข้อมูลที่บันทึกได้; หลาย connection เห็นสถานะอ่านที่เปลี่ยน
- session หมดอายุ/เพิกถอนปิด stream และ heartbeat ไม่ยืดอายุ session

ใช้ชุดทดสอบยืม/ซ่อม/auth เดิมร่วมกับ tests ของโมดูลใหม่และ integration ที่ฐานข้อมูลทดสอบ ตรวจ schema/build ตาม scripts ของ repo ก่อนส่งงาน

## 8. ข้อจำกัดและข้อมูลที่ตรวจแล้ว

- ยังไม่มีตาราง/โมดูล notification BE ปัจจุบันมี Nest, Prisma และ RxJS; @nestjs/schedule เป็น dependency ที่เสนอเพิ่มสำหรับงานตรวจเวลา
- วันคืนของฟอร์มขอยืมเองและฟอร์มศูนย์ถูกส่งต่างรูปแบบ แต่รอบนี้ยึด timestamp ที่อยู่ในฐานข้อมูลและไม่แก้ FE
- ฟอร์มขอยืมเองส่งวันคืนว่างได้ และ BE เก็บ null ได้ ไม่พบขั้นตั้งวันคืนภายหลังใน approve/handover; รอบนี้แก้เฉพาะการข้าม notification ตามเวลา
- ไม่ได้ตรวจข้อมูลจริงในฐานข้อมูลว่ามีรายการ null หรือการยืมระยะสั้นใช้งานจริง การออกแบบรองรับตามโค้ดที่อนุญาต
- ตรวจ flow ซ่อมไม่ได้แล้ว: วินิจฉัย → ช่างส่งเครื่องขั้น 5 → พัสดุรับผ่าน complete-unrepairable → ปิดงาน/รอจำหน่าย จึงตัดแจ้งเตือนรับคืนออกตามคำยืนยัน
- เริ่มแบบหนึ่ง instance ตามที่ตกลง หากเปลี่ยนเป็นหลาย instance ต้องออกแบบการส่งข้าม instance และการรันงานตามเวลาเพิ่มเติม
- ประวัติใน DB ไม่เท่ากับการส่ง SSE ทุก frame สำเร็จ หาก BE หยุด งานตรวจเวลาทำงานต่อเมื่อเริ่มใหม่ และผู้เรียกโหลดข้อมูลล่าสุดเมื่อ reconnect
- ไม่ย้อนหลังสร้างแจ้งเตือนธุรกิจจากคำขอเก่าทั้งหมด; งานตรวจเวลาเริ่มครอบคลุมรายการ BORROWED ที่ยังเข้าเกณฑ์อยู่ตามข้อมูลปัจจุบัน

แหล่งตรวจใน repo: src/asset-borrow/asset-borrow.service.ts, src/asset-borrow/asset-borrow.controller.ts, src/repairs/repairs.service.ts, prisma/schema/borrow.prisma, prisma/schema/repair.prisma, prisma/seed-reference.ts และ src/auth/session-lifetime.service.ts รวมถึง FE ที่อ่านเพื่อตรวจรูปแบบข้อมูลและ flow โดยไม่ได้แก้ไฟล์ FE

## 9. สเปกสำหรับพัฒนาต่อ

ผู้ใช้เรียก to-spec ให้สังเคราะห์บทสนทนาและแผนนี้เป็นสเปก และยืนยันให้ใช้ API/SSE กับฐานข้อมูลทดสอบจริงเป็นจุดทดสอบหลัก สเปกใน local issue tracker รวมกฎธุรกิจและรายละเอียดการพัฒนาที่จำเป็นแล้ว

เอกสารนี้เก็บที่มาของแผน งานรอบนี้เป็นการเขียนสเปก ไม่ใช่ implementation หรือการเปลี่ยน FE
