The successful public Asset response is cacheable for 30 days, not the original desired exact `public, max-age=31536000, immutable` one-year value. **Scoped decision (user, 2026-10-03): accept the observed 30-day Asset byte cache** because Asset images are public and replacement uses a new versioned URL. This does not approve the Employee Photo byte response. Cloudinary describes 30-day caching for uploaded assets on its shared `res.cloudinary.com` distribution and 365-day caching for private CDN/CNAME delivery; the latter is an Advanced-plan option with additional setup/cost. Its documented Upload API `headers` parameter supports `Link`, `Authorization`, and `X-Robots-Tag`, not `Cache-Control`. These sources do not establish an application-level override for the current shared-CDN route. See [Cloudinary caching defaults](https://cloudinary.com/glossary/caching-images), [advanced CDN options](https://cloudinary.com/documentation/advanced_url_delivery_options), and the [Upload API reference](https://cloudinary.com/documentation/image_upload_api_reference).

The signed Employee Photo download also returned `public, max-age=2592000` on success. The test proves a **fresh** request after expiry was denied; it does not prove already delivered bytes are removed from a browser or intermediary cache. Under [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html), `public` permits a shared cache to store a response, subject to the other caching rules; no shared-cache reuse was measured in this run. Cloudinary states that private download requests bypass its CDN and can use twice the bandwidth of CDN delivery, but this does not change the observed response header. See [Cloudinary media access control](https://cloudinary.com/documentation/control_access_to_media).

**Approved Employee Photo policy — 2026-10-04:** use the documented direct-browser fetch approach below to prevent caching for controlled HAMS loads, accepting that the provider response header remains observed as `public, max-age=2592000`. This is a scoped client-request policy, not permission for the HAMS display flow to use 30-day HTTP caching. Do not relabel the headers as one-year Asset caching or private/no-store Employee Photo byte responses. HAMS's grant response remains `private, no-store`; it does not control Cloudinary's byte-response header. No account-specific bandwidth charge was measured, and this decision does not change provider settings or runtime configuration. See [ADR 0005](adr/0005-employee-photo-cache-and-isolated-fe-handoff.md).

### Documentation-based delivery option (no Support request required)

The user requested a solution from Cloudinary documentation without contacting Support. The documented download options do not list a response `Cache-Control` override. Isolated synthetic probes confirmed that `attachment=true` and `GET|POST /asset/download` still returned `public, max-age=2592000`; neither is a header fix. Token/cookie access requires premium provider activation and is not a drop-in option for this request.

An actual isolated Edge probe successfully fetched the existing authenticated grant with Fetch `cache: 'no-store'`, explicit request `Cache-Control: no-store`, and `credentials: 'omit'`. CORS permitted the header, the JPEG Blob decoded, and a default-cache fetch of the identical grant after expiry returned network 401. Both synthetic provider runs completed exact-object cleanup. See [documentation research and probe evidence](cloudinary-employee-photo-cache-options.md) for the sources, delivery pattern, and limits.

Accepted scope: preserve Backend grant issuance/expiry and load Employee Photos through a shared Frontend helper using `cache: 'no-store'`, explicit request `Cache-Control: no-store`, and `credentials: 'omit'`. Display session-memory Blob URLs and clear/revoke them on replacement/logout/account switch/unmount; prevent stale async responses from restoring an old image. This controls the HAMS request path; it does not change Cloudinary's response header, erase downloaded copies, or impose no-store on copied-grant navigation. CORS failures must surface without a direct-image fallback. Actual Frontend integration and lifecycle acceptance remain pending in 06/07. No Support request is required.
