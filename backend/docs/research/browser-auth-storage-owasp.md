# Browser authentication storage for HAMS: OWASP comparison

Date: 2026-09-20

## Decision summary

For the browser-only React client, HAMS should stop returning its session token to browser JavaScript and stop persisting that token in `localStorage`. Prefer BetterAuth's server-managed session carried in a `Secure`, `HttpOnly`, explicitly `SameSite` cookie. This follows OWASP's direct guidance not to store authentication tokens, session IDs, JWTs, refresh tokens, or credentials in Web Storage, because any JavaScript executing in the origin can read them; OWASP names hardened cookies or a Backend-for-Frontend pattern as the preferred alternatives ([OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#the-localstorage-api), [OWASP HTML5 Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html#local-storage)).

This is a recommendation about **where the browser keeps and how it sends the session credential**, not about whether the credential is JWT or opaque. A JWT or an opaque session ID can be transported in an `Authorization` header or a cookie. HAMS currently returns BetterAuth's `result.token` from `src/auth/auth.controller.ts`; the repository does not establish that this value is a JWT, so it should be described as a session token unless its format is independently verified.

## Current HAMS posture

- `src/auth/auth.controller.ts` returns `result.token` in the sign-in JSON response. The React client then stores it in `localStorage` and attaches `Authorization: Bearer <token>` (the client behavior is supplied project context).
- `src/auth/auth.ts` enables BetterAuth's `bearer()` plugin.
- `src/main.ts` currently enables credentialed CORS with `origin: true`. Before browser cookie authentication is enabled, this must become an exact allowlist of HAMS frontend origins. OWASP says credentialed CORS must allow only a small set of origins definitively controlled by the application; permitting broad subdomain patterns is also risky because a taken-over subdomain can bypass the intended boundary ([OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#custom-headers-and-cors)).

## Security trade-off

| Concern | `localStorage` + Bearer header | `HttpOnly` session cookie |
|---|---|---|
| Token theft through XSS | JavaScript can read and exfiltrate the token. The attacker can replay a bearer credential from another browser until it expires or is revoked. OWASP explicitly advises against storing session/auth tokens in `localStorage` or `sessionStorage` ([Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#the-localstorage-api)). | `HttpOnly` prevents JavaScript from reading the cookie, reducing credential exfiltration. It does **not** neutralize XSS: malicious script running in the page can still cause authenticated requests while the victim's page/session is active ([Session Management: HttpOnly](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#httponly-attribute)). |
| Classic CSRF | A cross-site form/image cannot normally invent the custom `Authorization` header, and Web Storage is not automatically included with requests. This reduces classic CSRF exposure, but does not protect against XSS or a dangerously permissive credentialed CORS policy ([OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#employing-custom-request-headers-for-ajaxapi)). | Browsers automatically attach matching cookies, so state-changing endpoints need an explicit CSRF defense. OWASP recommends a synchronizer token for stateful software, a signed double-submit cookie for stateless software, or a carefully enforced custom-header pattern for AJAX/API traffic; `SameSite` is normally defense in depth, not a substitute ([OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#introduction)). |
| Persistence after browser restart | `localStorage` persists until explicitly cleared, extending the useful lifetime of a stolen token. | Persistence is controlled by cookie lifetime and server-side session lifetime. `HttpOnly` protects confidentiality from JavaScript; server-side expiry and revocation still remain necessary ([OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#cookies)). |
| Scope | Web Storage is shared across the whole origin and cannot be restricted by URL path ([OWASP HTML5 Security](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html#local-storage)). | Cookies can be scoped by host and path. OWASP recommends omitting `Domain` and using the most restrictive practical `Path` ([Session Management: Domain and Path](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#domain-and-path-attributes)). |

The cookie option is therefore not “XSS solved”; it changes the worst XSS outcome from an easily exported, replayable session credential to abuse largely constrained to the compromised browser context. HAMS still needs normal XSS prevention and short, revocable server sessions.

## Required controls for the HAMS cookie design

1. **HTTPS everywhere and `Secure`.** Send authenticated traffic only over TLS, set `Secure`, and deploy HSTS after validating the HTTPS deployment. OWASP calls `Secure` mandatory for protecting a cookie session ID from network disclosure ([Session Management: Secure](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#secure-attribute)).
2. **`HttpOnly`.** The React application must not receive or read the session credential. Sign-in should establish the session using `Set-Cookie`; frontend requests should use the browser's credential mode rather than constructing an `Authorization` header ([Session Management: HttpOnly](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#httponly-attribute)).
3. **Explicit `SameSite`.** Prefer `Strict` if HAMS navigation and deployment allow it; otherwise use `Lax` after testing required login/navigation flows. Never use `SameSite=None` without `Secure`. Do not rely on a browser default, and normally combine `SameSite` with a CSRF control ([Session Management: SameSite](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#samesite-attribute)).
4. **Narrow host/path scope.** Omit `Domain` so the cookie is host-only, and set the narrowest practical `Path`. If a host-wide session is required, an OWASP-recommended `__Host-` cookie uses `Secure`, no `Domain`, and `Path=/`; do not claim both `__Host-` and a narrower path because the prefix requires `/` ([Session Management: cookie prefixes](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#samesite-attribute), [Domain and Path](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#domain-and-path-attributes)).
5. **CSRF protection on every state change.** First use any maintained protection supplied by BetterAuth/framework. For HAMS's JSON API, use a synchronizer token carried in a custom header, or a session-bound HMAC signed double-submit token; also reject unsafe cross-site requests using `Origin`/`Referer` and/or Fetch Metadata as defense in depth. Never mutate state through `GET` ([OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#token-based-mitigation)).
6. **Exact CORS allowlist.** Replace `origin: true` with the exact production and explicitly needed development React origins, keep credentialed CORS only for those origins, and allow only required methods/headers. A custom-header CSRF defense is only as strong as this allowlist because any allowed origin can send that header after preflight ([OWASP CSRF Prevention: Custom Headers and CORS](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#custom-headers-and-cors)).
7. **Lifecycle controls.** Rotate the session ID after authentication and privilege changes, expire idle/absolute sessions server-side, revoke on logout/password reset/account disable/2FA reset, and return `Cache-Control: no-store` on responses containing session credentials ([OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#session-id-life-cycle)).

## Does OWASP ban Bearer tokens?

No. OWASP describes bearer tokens as simple and widely adopted and gives controls for using them; it also notes that possession is sufficient for use and recommends audience restriction and, for higher-risk cases, sender-constrained tokens such as DPoP or mTLS ([OWASP OAuth 2.0 Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/OAuth2_Cheat_Sheet.html#terminology)). The relevant HAMS issue is narrower: OWASP explicitly discourages placing browser session/authentication credentials in Web Storage. Bearer authorization remains reasonable for explicitly supported non-browser API clients if HAMS actually needs them, with TLS, short lifetime, narrow audience/scope, and separate client policy. It should not be the default browser-session design merely because the server supports the BetterAuth bearer plugin.

## HAMS-specific recommendation

1. Use BetterAuth's cookie-based session for the React browser client; do not include the session token in sign-in JSON and remove the browser's `localStorage`/`Authorization` handling.
2. Configure the session cookie with the controls above and make the frontend send credentialed requests.
3. Add a real CSRF control and exact CORS allowlist before switching production traffic. The present `origin: true` configuration is not an acceptable final state for credentialed cookie auth.
4. Keep any Bearer-token route only for a documented non-browser client need; do not expose both mechanisms accidentally across every endpoint.
5. Treat the planned 2FA trusted-browser credential as a separate high-value cookie and harden it at least as strongly. 2FA does not repair a stolen post-login session token: an attacker replaying that token may inherit the already-authenticated session until it expires or is revoked. OWASP recommends reauthentication for sensitive actions and session/token rotation after reauthentication ([OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#require-re-authentication-for-sensitive-features)).
