# การกู้ 2FA เมื่อเหลือ ADMIN ที่ลงทะเบียนแล้วเพียงคนเดียว

วันที่ค้นคว้า: 24 กันยายน 2569 (2026-09-24)

## คำตอบสั้น

**การยอมให้จำนวน ADMIN ที่ลงทะเบียน 2FA แล้วลดจาก 2 เป็น 1 ชั่วคราวระหว่างกู้บัญชี ไม่ได้ขัดกับข้อกำหนดจำนวนคนของ OWASP หรือ NIST เพราะทั้งสองแหล่งไม่ได้กำหนดว่าแอปพลิเคชันต้องมี ADMIN อย่างน้อย 2 คน** เกณฑ์ 2 คนเป็นนโยบายความพร้อมใช้งานและการลดจุดล้มเหลวเดียวของ HAMS เอง การยกเว้นแบบแคบสำหรับเหตุสูญเสียทั้ง Authenticator และ Recovery Codes จึงเป็นการตัดสินใจจากความเสี่ยงของระบบ ไม่ใช่การยกเว้นมาตรฐานสากล ([OWASP MFA Cheat Sheet — Resetting MFA](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html#resetting-mfa), [NIST SP 800-63B-4 §4.2](https://pages.nist.gov/800-63-4/sp800-63b.html#account-recovery)).

OWASP ระบุว่าต้องมีวิธีกลับเข้าใช้เมื่อทำปัจจัยที่สองหาย และยกตัวอย่าง Recovery Codes แบบใช้ครั้งเดียว, การติดต่อทีมสนับสนุนที่ตรวจตัวตนอย่างรัดกุม, หรือให้ผู้ใช้ที่เชื่อถือได้อีกคนรับรอง แต่เตือนว่าช่องกู้ต้องไม่กลายเป็นช่องข้าม MFA เพื่อยึดบัญชี และไม่มีวิธีเดียวที่เหมาะทุกองค์กร ([OWASP MFA Cheat Sheet — Resetting MFA](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html#resetting-mfa)).

## ความปลอดภัยของข้อเสนอ HAMS

การให้ ADMIN อีกคนที่ยังใช้ 2FA ได้ตรวจตัวตนของผู้ขอกู้นอกระบบ แล้วยืนยัน TOTP ก่อนสั่งรีเซ็ต **สอดคล้องกับตัวอย่างแนวทางของ OWASP ในเชิงหลักการ** แต่ความแข็งแรงจริงขึ้นอยู่กับขั้นตอนตรวจตัวตนที่กำหนดและปฏิบัติได้จริง ไม่ควรถือว่าเพียงมี ADMIN อีกคนก็กู้ได้อย่างปลอดภัยโดยอัตโนมัติ ([OWASP MFA Cheat Sheet — Resetting MFA / Changing MFA Factors](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html#resetting-mfa)).

มาตรการที่ควรใช้ร่วมกันสำหรับข้อยกเว้นนี้:

1. จำกัดให้เป็น **การรีเซ็ตเพื่อกลับไปลงทะเบียน 2FA ใหม่เท่านั้น**; บัญชีที่ถูกรีเซ็ตห้ามเข้า Business API จนยืนยัน TOTP ใหม่สำเร็จ และไม่ให้ผู้ช่วยกู้เห็น Secret/Recovery Codes ใหม่ของเจ้าของบัญชี การจำกัดสิทธิ์นี้เป็นข้อเสนอออกแบบของ HAMS เพื่อไม่ให้การรีเซ็ตเท่ากับปล่อยบัญชีที่ไม่มี MFA ใช้งานตามปกติ โดยอิงความเสี่ยงที่ OWASP เตือน ([OWASP MFA Cheat Sheet — Resetting MFA](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html#resetting-mfa)).
2. ADMIN ผู้ช่วยกู้ต้องยืนยัน TOTP สดก่อนคำสั่ง และต้องมีขั้นตอนยืนยันตัวจริงนอกระบบที่บันทึกได้ (เช่น พบตัวพร้อมบัตรเจ้าหน้าที่/ให้ผู้รับผิดชอบยืนยันตามกระบวนงานโรงพยาบาล); ห้ามใช้เพียงคำร้องทางแชตหรือเบอร์โทรที่ผู้ร้องแจ้งเอง นี่เป็นการประยุกต์หลัก “rigorous process” ของ OWASP ไม่ใช่สูตรเฉพาะที่ OWASP บังคับ ([OWASP MFA Cheat Sheet — Resetting MFA](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html#resetting-mfa)).
3. เพิกถอน Session และ Trusted Browser ทั้งหมดของบัญชีที่ถูกกู้, ทำ Audit Log ว่าใครรีเซ็ตให้ใคร/เมื่อใด/เหตุผล, และแจ้งเจ้าของบัญชีผ่านช่องทางที่บันทึกไว้หลังรีเซ็ตและหลังผูกปัจจัยใหม่; OWASP แนะนำการแจ้งเมื่อเปลี่ยนปัจจัย และ NIST กำหนด notification สำหรับ account recovery ในกรอบมาตรฐานของตน ([OWASP MFA Cheat Sheet — Changing MFA Factors](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html#changing-mfa-factors), [NIST SP 800-63B-4 §§4.2, 4.6](https://pages.nist.gov/800-63-4/sp800-63b.html#account-recovery)).
4. ระหว่างเหลือ ADMIN ที่ลงทะเบียนแล้วเพียง 1 คน ให้บล็อกการลบ/ปิดใช้งาน/เปลี่ยน Role ของคนสุดท้าย และแสดงสถานะให้ผู้รับผิดชอบทราบจนคนที่กู้ลงทะเบียนใหม่สำเร็จ; นี่เป็นมาตรการลดความเสี่ยงด้านความพร้อมใช้งานของ HAMS ไม่ใช่ข้อกำหนดตัวเลขจาก OWASP/NIST.

**ข้อจำกัดสำคัญ:** อย่าอ้างว่า workflow “ADMIN อีกคนตรวจตัวตนนอกระบบ + TOTP ของ ADMIN คนนั้น” ผ่านข้อกำหนดการกู้บัญชี **NIST AAL2** โดยอัตโนมัติ NIST SP 800-63B-4 กำหนดทางเลือกเฉพาะ เช่น Recovery Codes สองวิธีต่างกัน, Recovery Code หนึ่งวิธีร่วมกับ Authenticator ของเจ้าของบัญชีที่ยังใช้ได้, หรือการพิสูจน์ตัวตนซ้ำเมื่อเดิมมีการพิสูจน์ตัวตนตามระดับที่กำหนด และให้วิเคราะห์/บันทึกความเสี่ยงสำหรับวิธีเฉพาะแอป การตรวจตัวตนโดยเพื่อนร่วมงานอย่างไม่เป็นทางการไม่เท่ากับ repeated identity proofing ตาม NIST; ความสอดคล้องกับมาตรฐานดังกล่าวต้องประเมินแยกหาก HAMS ตั้งใจอ้าง AAL2 ([NIST SP 800-63B-4 §4.2](https://pages.nist.gov/800-63-4/sp800-63b.html#account-recovery)).

## ภาระงานและทางเลือก

ในสถานการณ์ปกติ **ไม่มีขั้นตอนเพิ่ม** สำหรับการล็อกอินหรือการทำงานประจำวันของ ADMIN; จะมีขั้นตอนพิเศษเฉพาะเมื่อ ADMIN ทำทั้ง Authenticator และ Recovery Codes หาย ซึ่งต้องประสาน ADMIN อีกคน ตรวจตัวตน กดรีเซ็ต แล้วให้เจ้าของบัญชีตั้งค่าใหม่ จึงช้ากว่าการล็อกอินทั่วไปโดยตั้งใจ ([NIST SP 800-63B-4 §4.2 ระบุว่า account recovery มักสะดวกน้อยกว่าการยืนยันตัวตนปกติ](https://pages.nist.gov/800-63-4/sp800-63b.html#account-recovery)).

เพื่อลดโอกาสต้องใช้ขั้นตอนนี้ ให้เก็บ Recovery Codes แบบออฟไลน์อย่างปลอดภัยและฝึกผู้ใช้ให้รู้วิธีใช้ก่อนเกิดเหตุ; NIST แนะนำให้มีวิธียืนยันตัวตนแยกกันอย่างน้อยสองวิธีเพื่อลดการต้องกู้บัญชี ([NIST SP 800-63B-4 §§4.1, 4.2](https://pages.nist.gov/800-63-4/sp800-63b.html#authenticator-event-management)). หากเหลือ ADMIN ที่ใช้ 2FA ได้เพียงคนเดียวแล้วคนนั้นหาย/ไม่พร้อมด้วย จะไม่มีผู้อนุมัติในแอป ต้องมีแผนฉุกเฉินนอกระบบที่แยกต่างหาก; ข้อยกเว้นนี้ไม่แก้เหตุสูญเสียพร้อมกันทั้งสองบัญชี (ข้อสรุปเชิงออกแบบของ HAMS).

**ข้อเสนอจากการค้นคว้า:** อนุญาตให้เหลือ 1 คนได้ระหว่างกู้ 2FA พร้อมมาตรการข้างต้น และคืนจำนวนเป็น 2 โดยเร็ว ไม่ต้องเพิ่มการยืนยันทุกครั้งให้ ADMIN ทุกคนเพียงเพื่อรองรับกรณีที่เกิดน้อย แต่ก่อนส่งมอบควรให้เจ้าของระบบ/ฝ่าย IT Security รับรองขั้นตอนตรวจตัวตนและแผนกรณี ADMIN ทั้งสองใช้การไม่ได้.

**มติแผน HAMS:** ใช้เกณฑ์ 2 คนเป็นเงื่อนไขก่อนส่งมอบและแนวปฏิบัติหลังเปิดใช้ ไม่บังคับเป็น invariant ตลอดเวลาในโค้ด; ป้องกันการลบ/ปิดใช้งาน/ลด Role ของ ADMIN คนสุดท้ายที่ยัง Active และผ่าน Enrollment. รายละเอียดการทำงานอยู่ใน [TASK.md](../../TASK.md).
