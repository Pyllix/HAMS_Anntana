# Ticket 08 — ผลตรวจรับ API และ performance

ตรวจเมื่อ 2026-10-12 บน PostgreSQL 17.10 ชั่วคราวในเครื่องพัฒนา ฐานทดสอบถูกแยกจากฐานข้อมูลของโปรเจกต์และลบทิ้งหลังจบการวัด

## ขอบเขตและวิธีวัด

- วัด API 12 กรณีในแต่ละชุดข้อมูล รวม 24 กรณี: รายการและ summary ของยืม–คืน, ครุภัณฑ์, งานซ่อม, อะไหล่, รายการผู้ใช้ และประวัติรับเข้า 3 แบบ
- ชุด small มีอะไหล่ 500, ครุภัณฑ์ 500, งานซ่อม 1,000, ประวัติรับเข้า 2,000, transaction อะไหล่ 5,000, การยืม 5,000 และผู้ใช้สังเคราะห์ 1,000 ราย
- ชุด scaled มีอะไหล่ 10,000, ครุภัณฑ์ 5,000, งานซ่อม 20,000, ประวัติรับเข้า 50,000, transaction อะไหล่ 100,000, การยืม 100,000 และผู้ใช้สังเคราะห์ 10,000 ราย
- อุ่นระบบ 3 ครั้งต่อกรณี วัดคำขอเดี่ยว 30 ครั้ง และวัด 50 คำขอที่ concurrency 5; p50/p95 เป็นเวลารับ HTTP response body ครบ
- จำนวน SQL คือจำนวน statement ต่อคำขอ; จำนวน DB rows คือแถวที่ query ส่งกลับรวมใน request ซึ่งรวม relation ที่จำเป็น ไม่ใช่จำนวนแถวที่ PostgreSQL ตรวจหรือสแกน
- รายการทุก API วัดด้วย page size 20; summary อ่านข้อมูลทั้งหมดเพื่อ aggregate ที่ฐานข้อมูลและตอบกลับเฉพาะจำนวนตามกลุ่ม
- เก็บ query plan 133 ชุด พร้อมยืนยัน auth guard สำหรับ transaction อะไหล่และประวัติรับเข้า (anonymous ได้ 401, department role ได้ 403)

จำนวน query, DB rows และ response bytes ของกรณีที่จับคู่กันเท่ากัน ไม่มีหลักฐานว่า Ticket 08 เพิ่มหรือลดข้อมูลที่ endpoint นี้อ่าน; ความต่างของเวลาเป็นผลวัดคนละรอบและไม่ควรตีความเป็นการปรับปรุงหรือถดถอยจากรอบสั้นนี้ รอบนี้มี paired before/after ที่ทำซ้ำได้เฉพาะประวัติรับเข้าจาก Ticket 07; API รายการที่เพิ่มหรือเปลี่ยน contract และ summary ใหม่รายงานผลหลังทำ พร้อมระบุว่าไม่มี baseline ที่เทียบได้ในชุดทดลองนี้ จึงไม่อ้างเปอร์เซ็นต์ที่ไม่มีฐานเปรียบเทียบ

## API write-flow และ correctness

PostgreSQL E2E ผ่าน 23/23 tests จาก 2 suites หลังแก้ล่าสุด โดยรวมการปฏิเสธ `evaluatedOnly=not-a-boolean` ด้วย HTTP 400 และยืนยันว่าค้นหางานด้วยชื่อช่างจะไม่รวมงานที่ความสัมพันธ์ช่างถูก soft-delete:

- ทำวงจรยืมจนคืนครบ แล้วอ่าน borrow/asset summaries ใหม่ในแต่ละสถานะ
- เปิดงานซ่อมและตรวจ summary; อนุมัติเบิกอะไหล่ผ่าน workflow แล้วตรวจ stock summary, จำนวนคงเหลือ, การคืนอะไหล่ และประวัติ transaction
- รับอะไหล่ผ่าน API แล้วตรวจยอดสต็อกและประวัติรับเข้าที่อ่านกลับได้
- แก้ผู้ใช้ผ่าน API แล้วค้นหาเจอค่าที่บันทึกใหม่
- ตรวจ route ที่ต้องจำกัดสิทธิ์ด้วย RolesGuard จริง ไม่ใช่ mock guard

การตรวจอื่น: unit run รายงาน 52/52 suites และ 468/468 tests ผ่าน; หลังพิมพ์ผล Jest แจ้งว่ามี async handle ค้างและ process ไม่ออกเอง จึงหยุด process หลังผลครบ. รายการยืม–คืน/ครุภัณฑ์/ซ่อม/อะไหล่/รับเข้า/ผู้ใช้มี PostgreSQL endpoint coverage รวมข้อมูลเกิน 100, ตัวกรองและ total ใช้เงื่อนไขเดียวกัน, ทดสอบลำดับหน้าที่มี timestamp เท่ากัน, ตรวจ summary ข้ามแผนก, และเลือกอะไหล่นอก 100 รายการแรกด้วย search กับ read-by-ID. ตรวจยืนยันใหม่เมื่อ 2026-10-12: TypeScript ตรวจผ่านและ Nest production build ผ่านเมื่อรันนอก sandbox โดยไม่แก้ source หรือ dependency. 4 errors ที่รายงานก่อนหน้าเกิดเฉพาะการรันใน sandbox ของเครื่องมือ (การ resolve/access dependency ต่างกัน); เทียบ compiler/โค้ดเดียวกันและปิด incremental cacheแล้ว ยืนยันว่าไม่ใช่ข้อผิดพลาดของโค้ดที่ต้องแก้.

## Lookup และขอบเขตการส่งมอบ

- lookup อ้างอิงขนาดเล็กและมีจำนวนจำกัด เช่น sections, company, budget types และ repair metadata โหลดเป็นชุดได้ ไม่เพิ่ม pagination ที่ไม่คุ้มกับข้อมูลขนาดนี้
- spare-part groups มี API page/limit อยู่แล้ว; เลือกอะไหล่ใช้ search/page และโหลดรายการที่เลือกด้วย ID; ผู้ใช้มี API search/page อยู่แล้ว จึงรองรับข้อมูลที่โตได้โดยไม่ต้องโหลดทุกแถว
- เอกสารนี้รับรองเฉพาะ BE/API ใน Ticket 08 ไม่มี browser/FE timing และไม่ได้รับรอง deployment บน VM ของโรงพยาบาล; การเชื่อมทุกตาราง/summary/lookup และตรวจผลบน FE เป็น Ticket 09
- ผลเป็น local synthetic workload; สเปกเครื่อง, cache, network, จำนวนผู้ใช้พร้อมกัน และข้อมูลจริงของโรงพยาบาลอาจทำให้เวลาเปลี่ยน ต้องวัดซ้ำด้วย workload UAT ก่อนใช้เป็น SLA
