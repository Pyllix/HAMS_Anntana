# วิเคราะห์ข้อมูลเดโม HAMS และช่องว่างของ seed

วันที่วิเคราะห์: 9 ตุลาคม 2569

วิเคราะห์จาก source ของ backend, Prisma schema, seed และ API ที่ลงทะเบียนใน `AppModule` เท่านั้น ไม่ได้รัน seed, อ่านข้อมูลฐานจริง, เรียกบริการภายนอก หรือยืนยันความพร้อมของ frontend จำนวนด้านล่างเป็นจำนวนที่ประกาศในสคริปต์ ไม่ใช่จำนวนแถวในฐานข้อมูลปัจจุบัน

## ข้อสรุป

`prisma/seed.ts` เตรียมข้อมูลพื้นฐานสำหรับเริ่มใช้งานได้ แต่ยังไม่ใช่ชุดข้อมูลสำหรับนำเสนอ workflow ครบระบบ โดยเฉพาะยืม–คืน, ต่ออายุ, งานซ่อม, ประวัติเบิก/คืนอะไหล่, โอนย้าย, จำหน่าย และการตั้งค่า 2FA

ควรแยกการเตรียมเป็นข้อมูลพื้นฐาน, ประวัติย้อนหลัง, รายการที่ดำเนินงานอยู่, และการเตรียมบัญชี/บริการภายนอก พร้อมตรวจความสัมพันธ์ก่อนนำเสนอ

## 2. ช่องว่างที่ควรแก้ก่อนเพิ่มรายการเดโม

### 2.1 สถานะเครื่องไม่มีรายการงานรองรับ

Seed ตั้ง Hamilton-G5 Medical และ Fisher & Paykel Airvo 2 เป็น BORROWED แต่ไม่มี `BorrowTransaction` และตั้ง Dräger Primus กับ Philips HeartStart FRx เป็น UNDER_REPAIR แต่ไม่มี `RepairJob`

ผลคืออาจเห็นสถานะในทะเบียน แต่ไม่มีใบยืมให้คืนหรือใบงานให้ช่างดำเนินการต่อ ควรสร้างรายการที่สัมพันธ์กันผ่าน flow หรือเปลี่ยนเครื่องเหล่านี้เป็นสถานะเริ่มต้น แล้วให้สคริปต์ workflow ปรับสถานะให้

แหล่งตรวจ: `seed.ts` บริเวณ 660–682, 870–892, 960–982, 1020–1042; [borrow service](../src/asset-borrow/asset-borrow.service.ts), [repair service](../src/repairs/repairs.service.ts)

### 2.2 รัน seed ซ้ำอาจเขียนทับสถานะงานและสต็อก

- เครื่องเดิมค้นจาก serialNo แล้ว update ข้อมูลทั้งชุด รวมสถานะและแผนก จึงอาจย้อนสถานะหรือแผนกที่เปลี่ยนผ่าน workflow แล้ว
- อะไหล่เดิมถูกตั้ง `qtyInStock` กลับเป็นค่าตั้งต้น แต่ไม่มีการสร้างประวัติรับเข้าให้ชดเชยการเปลี่ยนยอดในสาขา update
- แม่แบบขั้นตอนที่ถือว่าเก่าถูก `deleteMany`; เมื่อมีงานซ่อมอ้างอิงอยู่ต้องตรวจความสัมพันธ์ก่อนปรับแม่แบบ
- Seed demo ไม่ได้ครอบทุกขั้นตอนใน transaction เดียว หากหยุดกลางทางอาจเหลือข้อมูลเตรียมเพียงบางส่วน
- คำสั่งชื่อ `prisma:reset` ปัจจุบันรัน generate → migrate dev → seed demo ไม่ได้ใช้ `migrate reset` และไม่ได้ล้างฐานทั้งหมดโดยตรง จึงไม่ใช่การกลับสู่ snapshot เริ่มต้นที่รับประกันได้

แหล่งตรวจ: `seed.ts` บริเวณ 1077–1100, 1197–1237, 1392–1400 และ `package.json`

### 2.3 วันที่และประวัติยังไม่รองรับจุดเด่นของระบบ

เครื่องทุกตัวเป็นคนละรุ่น และยังไม่มีประวัติยืมใน 90 วันล่าสุด ระบบแนะนำอาจคืนตัวเลือกเครื่องเดียว แต่ไม่มีคู่เปรียบเทียบสำหรับ Smart Swap

วันที่รับเครื่องส่วนใหญ่เป็นปี 2022–2024 และมีเครื่องเก่าปี 2015 แต่ไม่มีค่าซ่อมหรือรายการเบิกย้อนหลัง ควรเพิ่มข้อมูลรายเดือนที่ใกล้วันนำเสนอ และใช้วันอ้างอิงเดียวกันทั้งชุด

ประกันของหลายเครื่องยังไม่หมด: viability ตรวจประกันก่อนตรวจค่าซ่อม การเพิ่มค่าซ่อมสูงให้เครื่องที่ยังมีประกันจึงอาจยังได้ VIABLE ตาม logic ปัจจุบัน

## 3. ข้อมูลที่ต้องเพิ่มแยกตามฟีเจอร์

รายการทั้งหมดในตารางนี้เป็นข้อเสนอสำหรับชุดเดโมใหม่ ยังไม่มีการสร้างข้อมูลเหล่านี้

| ฟีเจอร์ที่มีใน backend | ข้อมูล/สถานการณ์ที่ต้องเพิ่ม | วิธีเตรียม |
|---|---|---|
| ทะเบียนครุภัณฑ์ เพิ่ม/แก้ไข/ค้นหา/กรอง/ข้อมูลแผนก | เพิ่มเครื่องพร้อมใช้งานสำหรับกรอกสด, เครื่อง DAMAGED/LOST/DISPOSAL, วันที่/ประกันหลากหลาย และจำนวนมากกว่าขนาดหน้ารายการที่เลือกใช้ | Seed ข้อมูลตั้งต้น; เพิ่ม/แก้ไขสดผ่าน UI |
| ข้อมูลพื้นฐาน CRUD และ restore ในหมวดที่รองรับ | รายการเดโมสำหรับแก้ไข/ลบที่ไม่ถูก workflow ใช้งาน และรายการ soft-deleted สำหรับสาธิต restore | Seed หรือ API; ไม่ใช้สถานะระบบสำคัญเป็นตัวอย่างลบ |
| ยืมแบบ self-service และ center-service | ใบยืมครอบคลุมทั้ง 8 สถานะ, PICKUP/DELIVERY, self_return/staff_pickup, คืนปกติ/ชำรุด, รายการเกินกำหนด และรายการยกเลิก/ปฏิเสธพร้อมเหตุผล | ประวัติจบแล้ว seed; รายการที่ต้องกดต่อสร้างผ่าน API ตาม flow |
| ต่ออายุยืม | ONLINE รออนุมัติ/อนุมัติ/ปฏิเสธ/ยกเลิก และ DESK ที่อนุมัติทันที; expectedReturnDate และ extensionCount/roundNumber ต้องตรงกับประวัติ | API บนรายการ BORROWED; ประวัติย้อนหลัง seed ให้ครบ |
| แนะนำเครื่องและ Smart Swap | เครื่องอย่างน้อย 3 ตัว model/type เดียวกัน ถ้ากรอง equipmentType ต้องตรงด้วย; ทุกตัว NORMAL/AVAILABLE; ประวัติใน 90 วันล่าสุด เช่น ใช้ 30, 10 และ 0 วัน พร้อมวันพักที่ต่างกัน | Seed เครื่องและประวัติคืนแล้ว; เปิดดูผลจริงผ่าน API/UI |
| รับแจ้งซ่อม แก้ไขก่อนมอบหมาย และ workload | งานรอรับ/รอมอบหมาย, งานเร่งด่วน/ฉุกเฉิน, ReportType Repair/Maintenance, ช่างบางคนมีหลายงานและบางคนว่าง, งานที่มอบหมายหลายช่าง | API เพื่อสร้างงานและ assignment ที่สัมพันธ์กัน |
| ซ่อมเอง SELF_REPAIR | งานวินิจฉัยแล้ว, กำลังซ่อม, รอส่งมอบ และปิดงาน; มี symptom/diagnosis/solution/ผู้ตรวจรับ/ประกันงานซ่อม | API; งานปิดย้อนหลัง seed |
| ซ่อมใช้อะไหล่ WITH_PARTS | ขอเบิก INTERNAL, EXTERNAL และผสม; รอพัสดุ, ส่งมอบอะไหล่แล้ว, รอปิดงาน; เพิ่มกรณีอะไหล่ไม่พอ และการไม่อนุมัติแล้วกลับมาวินิจฉัยใหม่ | API พร้อม stock-in เมื่อจะสาธิตรับเข้าคลัง |
| ส่งซ่อม OUTSOURCE | รอพัสดุ, อยู่บริษัท, รับคืนทดสอบ, งานปิดแล้ว; companyId/billNo/repairCost และผู้รับคืน | API; ประวัติปิดงาน seed |
| ซ่อมไม่ได้ UNREPAIRABLE | งานรอส่งซาก, พัสดุยืนยันรับมอบ, เครื่อง WAIT_DISPOSAL พร้อมสถานที่พัก | API รวม complete-unrepairable; แยกจากเครื่องที่จะเสนอจำหน่ายผ่าน viability |
| ยกเลิกงานซ่อม / คืนอะไหล่ | งานที่เข้าเงื่อนไขยกเลิก และงานที่เบิกจริงแล้วเหลืออะไหล่คืนได้ | API; ตรวจยอดคืนไม่เกินยอดเบิกสุทธิ |
| สต็อกอะไหล่และประวัติ | เพิ่มยอดศูนย์, ยอดเท่าจุดขั้นต่ำ, รับเข้าหลายรอบ, PENDING_WITHDRAW/WITHDRAW/RETURN และวันย้อนหลัง | Seed ประวัติที่ครบ; รับ/เบิก/คืนสดผ่าน API/UI |
| วิเคราะห์ความคุ้มค่า | ชุดตัวอย่างทุกเหตุผลหลักตามหัวข้อ 4; มีประวัติงานซ่อม ค่าซ่อมภายนอก และเบิก/คืนจริง | Seed ประวัติ แล้วตรวจผลคำนวณผ่าน API |
| เสนอจำหน่ายและบันทึกจำหน่าย | เครื่องไม่ติดงานสำหรับเสนอใหม่, เครื่อง WAIT_DISPOSAL สำหรับบันทึกจำหน่าย, เครื่อง DISPOSAL ที่มีเอกสารจริง | API; ประวัติจำหน่าย seed ทั้งระเบียน Disposal และสถานะเครื่อง |
| โอนย้ายและประวัติ | เครื่องพร้อมโอน, เครื่องเคยโอน 1–2 ครั้ง พร้อมต้นทาง/ปลายทาง/เลขเอกสาร/ผู้ทำรายการ; แผนกปัจจุบันตรงกับการโอนล่าสุด | API; ประวัติ seed แบบสัมพันธ์กัน |
| สถานะสูญหายและ cascade | เครื่องที่ยืมอยู่กับอีกเครื่องที่กำลังซ่อม สำหรับแสดงว่าการเปลี่ยนเป็น LOST ยกเลิกรายการที่ค้างและทำให้ไม่พร้อมใช้งาน | เตรียมด้วย API; เปลี่ยน LOST สดบนชุดเฉพาะนี้ |
| พยากรณ์งบและอายุขัย | ค่าใช้จ่ายกระจาย 12–18 เดือนใกล้วันนำเสนอในอย่างน้อย 3 แผนก; มีทั้งราคาซื้อและ WITHDRAW; เครื่องยังไม่ครบอายุ/ใกล้ครบ/เกิน useful life | Seed ประวัติและวันที่; ตรวจ Gemini และกราฟจริง |
| ผู้ใช้และสิทธิ์ | บัญชีแผนก A/B มีข้อมูลของแต่ละแผนก, ผู้ใช้สำหรับแก้ role/reset/delete/restore, ผู้ใช้ยังไม่ยืนยันอีเมล, บัญชีสำหรับตั้ง 2FA ใหม่ | Seed ตัวอย่าง; การกระทำและยืนยันอีเมลผ่าน flow จริง |
| รูปเครื่องและรูปพนักงาน | รูปเครื่องที่ผูกผ่าน upload flow, พนักงานมีรูป/ไม่มีรูป, รูปใหม่สำหรับเปลี่ยนและ preview | ไฟล์ตัวอย่าง + upload/complete/claim ผ่าน API/UI; URL เดิมไม่พิสูจน์ flow อัปโหลด |
| Login/2FA/Recovery/Trusted browser/Step-up | บัญชีตั้ง 2FA แล้วและยังไม่ตั้ง, recovery code สำหรับใช้ครั้งเดียว, browser ที่เชื่อถือได้, ADMIN 2 คนที่ enroll แล้วสำหรับ assisted reset | เตรียมผ่าน auth flow และ browser จริง; ไม่ seed session/token เพื่อข้ามเงื่อนไข |

สำหรับกรณีที่ต้องแสดงคำขอรออนุมัติ ควรมีตัวอย่างแยกจากรายการที่ใช้เดโมปฏิเสธหรือยกเลิก เพื่อไม่ให้การเดโมหนึ่งทำให้กรณีถัดไปหายไป

## 4. ชุดข้อมูลสำหรับฟีเจอร์คำนวณ

### แนะนำเครื่อง

- A: ใช้สะสม 30 วันใน 90 วันล่าสุด คืนล่าสุด 2 วันก่อน
- B: ใช้สะสม 10 วัน คืนล่าสุด 15 วันก่อน
- C: ไม่เคยยืมใน 90 วันล่าสุด รับเข้ามา 45 วันก่อน
- A/B/C อยู่ type/model เดียวกันและ NORMAL/AVAILABLE ประวัติที่ seed เป็นการยืมที่คืนแล้ว มีช่วงเวลาถูกต้องและไม่ทับซ้อนกันของเครื่องเดียว
- ควรได้ C เป็นอันดับแรก; เลือก A ควรเกิด nudge เพราะต่างจาก C เกิน 3 วัน
- เตรียมคู่ที่ใช้งานต่างกันน้อยและวันพักใกล้กัน เพื่อแสดงกรณีไม่มีข้อเสนอให้สลับ

อ้างอิง: `getBorrowRecommendations()` และ `checkSwapRecommendation()` ใน [borrow service](../src/asset-borrow/asset-borrow.service.ts)

### ความคุ้มค่าซ่อม

กำหนดอายุให้สัมพันธ์กับ useful life และใช้เครื่องหมดประกันในกรณีที่ต้องให้ผลจากค่าซ่อม/ความถี่ทำงาน

| กรณี | ข้อมูลตัวอย่าง | ผลที่ต้องตรวจ |
|---|---|---|
| ประกันยังใช้ได้ | วันสิ้นสุดประกันในอนาคต แม้มีค่าซ่อมสูง | VIABLE ตามลำดับกฎปัจจุบัน |
| ค่าซ่อมต่ำ | ราคา 100,000 ค่าซ่อมสุทธิ 20,000 อายุยังไม่เกิน useful life | VIABLE |
| ค่าซ่อมระดับเฝ้าระวัง | ราคา 100,000 ค่าซ่อมสุทธิ 55,000 อายุยังไม่เกิน useful life | WARNING |
| ค่าซ่อมสูง | ราคา 100,000 ค่าซ่อมสุทธิ 75,000 | UNVIABLE |
| ซ่อมถี่ | อายุยังไม่เกิน useful life ค่าซ่อมต่ำ แต่มีอย่างน้อย 3 งานใน 12 เดือน | WARNING |
| เครื่องเก่าและซ่อมซ้ำ | อายุเกิน useful life และมีอย่างน้อย 3 งานสะสม หรือค่าซ่อมอย่างน้อย 50% | UNVIABLE |
| บริจาคราคา 0 | ราคา 0 อายุเกิน useful life และอย่างน้อย 3 งานสะสม | UNVIABLE; อัตราค่าซ่อมไม่ใช้การหารด้วยศูนย์ |

ข้อมูลสามารถใช้ร่วมกับงานซ่อมย้อนหลังและรายงานค่าใช้จ่ายได้ ไม่ต้องเพิ่มเครื่องทุกกรณีแยกต่างหากโดยไม่จำเป็น

ค่าซ่อมสะสมของ viability = repairCost ภายนอก + มูลค่า WITHDRAW − มูลค่า RETURN; PENDING_WITHDRAW ไม่นับเป็นต้นทุนจริง

อ้างอิง: `evaluateViability()` และ SQL aggregate ใน [viability service](../src/asset-viability/asset-viability.service.ts)

### พยากรณ์และรายงานค่าใช้จ่าย

- เพิ่มข้อมูลราคาซื้อตาม receivedDate และอะไหล่ WITHDRAW ตาม txnDate ในหลายเดือน เพื่อให้เห็นความต่างระหว่าง acquisitions กับ repairs และการจัดอันดับแผนก
- ข้อมูล seed ปัจจุบันอาจแสดงค่าใช้จ่ายจากราคาซื้อได้อยู่แล้ว แต่ยังไม่มีประวัติเบิกจริงให้เกิดเส้นค่าซ่อมที่มีรายละเอียด
- `historyMonths` เลือกเดือนล่าสุดที่มีข้อมูลจากผล query ไม่ใช่การรับประกันว่าจะเป็น 12 เดือนปฏิทินล่าสุด จึงควรเติมข้อมูลเดือนใกล้วันนำเสนอและไม่วางเดือนอนาคตในประวัติจริง
- Forecast ปัจจุบันอ่านราคาซื้อกับ WITHDRAW ไม่ได้รวม repairCost ภายนอกหรือหัก RETURN แบบ viability; เติมเฉพาะค่าบิลซ่อมจะไม่เพิ่มค่าซ่อมในกราฟนี้
- การจัดแผนกรายจ่ายให้ความสำคัญกับ asset.section_id ปัจจุบัน ดังนั้นควรแยกเครื่องเดโมโอนออกจากชุดกราฟที่ต้องการตัวเลขคงที่
- ต้องตรวจ `GEMINI_API_KEY`, model ที่เรียกได้ และเครือข่าย; seed อย่างเดียวรับประกันผลพยากรณ์ไม่ได้

อ้างอิง: [forecast service](../src/forecast/forecast.service.ts)

## 5. ข้อมูลที่ต้องเตรียมผ่าน flow จริง

### บัญชีและ 2FA

ADMIN, PARCEL_STAFF และ ASSET_CENTER_STAFF ต้องตั้ง 2FA จน enrollmentComplete เป็น true ก่อนใช้ Business API บนฐานใหม่ seed มีเพียง credential account และ emailVerified=true จึงยังไม่พร้อมข้ามหน้าล็อกอินเข้าเดโมธุรกิจทันที

ควร enroll บัญชีธุรกิจที่จะใช้ล่วงหน้า และแยกบัญชีทิ้งสำหรับเดโมการตั้งครั้งแรก/Recovery/เปลี่ยน authenticator/เปลี่ยนรหัสผ่าน/เปลี่ยน role/ลบและกู้คืน ไม่ทำกับบัญชีหลักกลางการนำเสนอ เพราะการกระทำบางอย่างเพิกถอน session/trusted browser

มี ADMIN 2 คนแล้ว แต่ถ้าจะสาธิต assisted reset ของ ADMIN ต้องตั้ง 2FA ทั้งสองคนจริง ใช้ ADMIN อีกคนทำรายการหลัง Step-up และคำนึงถึงเงื่อนไขห้าม reset ตัวเอง/ห้ามทำให้เสีย ADMIN ที่ enroll คนสุดท้าย

Trusted browser ต้องมีทั้งข้อมูลฝั่ง server และ cookie ใน browser; การ seed แถว TrustedDevice อย่างเดียวไม่ได้ทำให้ Profile ที่เปิดไว้เชื่อถือได้ การสาธิต revoke และ session lifetime ต้องตรวจพฤติกรรมจริง

Email verification ต้องมีบัญชี emailVerified=false แยก และกล่องรับอีเมลเดโม/SMTP ที่ใช้ได้ seed เดิมตั้ง emailVerified=true ทุกบัญชี ส่วน SecurityAuditLog ที่เกิดจากการ reset ควรเกิดจากการกระทำจริง; ไม่พบหน้ารายงาน audit โดยเฉพาะใน API ที่ลงทะเบียน

อ้างอิง: [two-factor service](../src/auth/two-factor.service.ts), [enrollment guard](../src/auth/mandatory-enrollment.guard.ts), [users service](../src/users/users.service.ts), [auth contract](./auth-api-contract.md)

### รูปภาพ

Seed ใช้ imageUrl ภายนอก แต่ไม่ได้สร้าง ImageUpload intent, complete/verify หรือ attachment metadata และไม่ได้ใส่รูปพนักงาน

เตรียมไฟล์ตัวอย่างแล้วอัปโหลดจริงทั้ง ASSET_IMAGE และ EMPLOYEE_PHOTO เพื่อเดโม preview/ผูกกับระเบียน/เปลี่ยนรูป/การอ่านรูปพนักงานหลังยืนยันตัวตน ตรวจ Cloudinary และการหมดอายุของ read grant ด้วย ข้อมูลสำหรับการล้างรูปเก่าเป็นงานภายใน ไม่ควรอ้างว่ามีหน้าจอเดโมหาก frontend ยังไม่มี

อ้างอิง: [images module](../src/images/images.module.ts), [image upload controller](../src/images/image-uploads.controller.ts), [image read service](../src/images/image-read.service.ts)

## 6. ขอบเขตของคำว่า “ครบทุก feature”

ยึด API และ module ที่มีใน backend เป็นรายการเริ่มต้น แล้วเทียบหน้าจอ frontend อีกครั้ง ไม่ใช้รายการ Planned Features ใน CONTEXT หรือ use case ในเล่มเป็นหลักฐานว่าฟีเจอร์นั้นพร้อมแล้ว

จาก AppModule/controller ที่ตรวจ ยังไม่พบ module/API เฉพาะสำหรับตรวจนับครุภัณฑ์, กระบวนการอนุมัติรายจ่ายโดย MANAGER แบบแยกต่างหาก, ระบบใบสั่งซื้อเต็มรูปแบบ, in-app notification, รายงานทั่วไป/ส่งออกไฟล์แบบแยก module หรือปฏิทินนัด PM/สอบเทียบ มีเพียงข้อมูล PM/Cal และ ReportType Maintenance ในทะเบียน/งานซ่อม ส่วนพยากรณ์และ viability มี API จริง

อาจมีการรวมข้อมูลหรือแสดงผลใน frontend จึงต้องยืนยันจาก frontend ก่อนสรุปว่าขาดฟีเจอร์ การเพิ่ม seed ไม่สามารถสร้าง API หรือหน้าจอที่ยังไม่มีได้ การอนุมัติ/จ่ายของใน flow ซ่อมปัจจุบันหลายขั้นเป็นหน้าที่ PARCEL_STAFF อย่าเตรียมบทนำเสนอว่า MANAGER ทำทุก approval โดยไม่ตรวจ endpoint

## 7. แนวทางเพิ่มชุดเดโม

1. คง seed reference สำหรับข้อมูลระบบไว้ และปรับ seed demo ให้ไม่ย้อนสถานะ/สต็อกของข้อมูลที่เดิน workflow ไปแล้วโดยไม่ตั้งใจ
2. เพิ่มชุด fixture ที่ระบุสถานการณ์: เครื่องสดสำหรับเดโม, เครื่องสำหรับแนะนำ, เครื่องสำหรับกราฟ/viability, เครื่องสำหรับโอน/จำหน่าย/สูญหาย และบัญชีสำหรับทดลองจัดการผู้ใช้
3. Seed ประวัติที่จบแล้วให้ครบทั้งข้อมูลหลัก ลูก ผู้กระทำ วันเวลา และยอดคงเหลือ ใช้วันอ้างอิงเดียวกัน; อนุญาตวันอ้างอิงที่กำหนดเพื่อซ้อมผลคำนวณซ้ำได้
4. สร้างรายการค้างผ่านสคริปต์ API ทีละรายการตาม role จริง รักษา cookie ของแต่ละบัญชี และทำ auth/CSRF ตาม contract ไม่สร้างหลายรายการพร้อมกันโดยสมมติว่า running number รองรับ concurrency แล้ว
5. เตรียม auth และ image ผ่าน flow จริง แยกขั้นตอนนี้จากการใส่ข้อมูลฐาน; เมื่อรัน fixture ครบแล้วอย่ารัน seed เดิมทับรายการที่เดิน flow แล้ว
6. บันทึก manifest สถานการณ์ → ID จริง → เลขเอกสาร → role → ขั้นตอนถัดไป → ผลที่คาดหวัง ไม่เดาเลข ID หรือใช้ UUID จากรอบก่อน
7. แยกการ rerun ที่รักษารายการเดิม ออกจากการกู้ snapshot เพื่อเริ่มใหม่ หากต้องการเลขเดิมทุกครั้ง ให้กู้ snapshot ชุดเริ่มต้นและตรวจข้อมูล browser/บริการรูปที่เกี่ยวข้องด้วย

ค่าประมาณสำหรับชุดครอบคลุม: ใช้บัญชีเดิม 28 คนเป็นฐาน เพิ่มบัญชีทดลองตามจำเป็น; ครุภัณฑ์รวมประมาณ 35–50 เครื่อง; ใบยืมประมาณ 20–30 รายการรวมประวัติแนะนำเครื่อง; extension อย่างน้อย 5 กรณี; งานซ่อมประมาณ 15–25 งานรวมประวัติ viability; transfer 3–5 รายการ; disposal 2–3 รายการ จำนวนนี้เป็นกรอบวางแผน ไม่ใช่เกณฑ์ตายตัว และต้องมีข้อมูลรายเดือนแยกเพิ่มตามกราฟที่ต้องการ

## 8. เกณฑ์ตรวจว่าชุดเดโมพร้อม

- เครื่องที่ BORROWED/RESERVED มีรายการยืม active ที่สัมพันธ์กัน และเครื่อง UNDER_REPAIR มีงานซ่อม active
- เครื่องที่มีประวัติคืนแล้วพร้อมใช้ไม่มีรายการค้างที่ขัดกับสถานะ; วันส่งมอบ/คืนเรียงถูกและไม่มีช่วงยืมทับซ้อนกันของเครื่องเดียว
- งานซ่อมมี assignment และขั้นตอนตามเส้นทางจริง ไม่มีการข้ามขั้น; ผู้ตรวจรับเป็นผู้แจ้งเดิมหรืออยู่แผนกที่เข้าเงื่อนไข
- การคืนชำรุดทำก่อนเปิดใบซ่อมของเครื่องที่อยู่ระหว่างยืม; เครื่องสำหรับจำหน่าย/โอนไม่ติดงานที่ระบบห้าม
- ยอดคงเหลืออะไหล่สอดคล้องกับการรับเข้า เบิกภายใน และคืนภายในจริง; pending/external ไม่ถูกนำไปหักสต็อกเหมือน internal withdrawal โดยไม่ตรวจ flow
- Recommendation มีหลาย candidate และมีทั้งกรณีเกิด/ไม่เกิด nudge
- Viability ได้ผลครบสามระดับและเหตุผลสำคัญ; อะไหล่ pending ไม่เพิ่มค่าซ่อมจริง
- Forecast มีหลายเดือนและหลายแผนก พร้อมผลจากบริการที่เรียกได้; ไม่คาดว่าตัวเลขเท่ากับ viability เมื่อฐานคำนวณต่างกัน
- Role และขอบเขตข้อมูลถูกต้องเมื่อสลับบัญชี; บัญชีธุรกิจที่บังคับ 2FA ผ่าน enrollment แล้ว
- รูปที่ใช้เดโมเปิดดูได้ และการอัปโหลด/ผูก/เปลี่ยนรูปผ่าน flow จริง
- รันเตรียมซ้ำแล้วไม่เพิ่มธุรกรรมซ้ำหรือทำให้สถานะ/สต็อกขัดกัน; manifest อ้าง ID และเลขที่มีอยู่จริง
- ซ้อมบทหลักผ่าน frontend ครบหนึ่งรอบ และเทียบหน้าจอทุกฟีเจอร์กับรายการในตารางก่อนเรียกว่า present ได้ครบ

การวิเคราะห์ครั้งนี้เพิ่มเฉพาะเอกสารฉบับนี้ ยังไม่ได้แก้สคริปต์ seed หรือสร้าง/เปลี่ยนข้อมูลในฐาน

อัปเดตหลังการวิเคราะห์: เพิ่มชุด `prisma:seed:presentation` แยกจาก seed เดิมแล้ว มีข้อมูลธุรกิจครบตามสถานการณ์หลักและโหมด dry-run ดู [คู่มือชุดนำเสนอ](./presentation-seed-guide.md) การลงฐานจริงและการเตรียม 2FA/รูปภาพ/บริการภายนอกยังต้องทำตามขั้นตอนในคู่มือ
